# Параллельные чаты в Jarvis/WebUI

Статус: план, не реализовано.
Записано: 2026-07-07 (после дня 27).

## Проблема

1. **Пока LLM генерирует ответ, нельзя переключиться на другой чат и вести параллельный
   диалог.** Сервер тут не виноват: Flask запущен с `threaded=True` и параллельные запросы
   обрабатывать умеет. Причина — один глобальный `JarvisAgent` с указателем
   `agent.current_session`: `POST /api/chat` пишет в «текущую» сессию, а не в конкретную.
   Переключение сессии во время генерации привело бы к записи ответа в чужую сессию —
   блокировка кнопки во фронте лишь маскирует эту гонку.
2. **Выбор модели влияет на все чаты.** `model`/`base_url`/`api_key` — атрибуты агента,
   а не сессии; настройки глобальны для всего сервера. То же с temperature/max_tokens.

Это не «нет асинхронности», а глобальное изменяемое состояние. asyncio не нужен —
потоков Flask достаточно.

## Идея решения: «агент на сессию»

Внутренности `JarvisAgent` не трогаем (он остаётся «одна сессия = одно состояние»).
В `webui/app.py` поднимаем реестр `{session_id: JarvisAgent}`; каждый агент навсегда
привязан к своей сессии. Понятие «текущая сессия сервера» исчезает — текущим чатом
управляет только фронтенд. Модель/провайдер, температура, FSM, MCP автоматически
становятся per-session, потому что живут в своём инстансе агента.

**Отвергнутый вариант:** сделать методы агента stateless (`chat(session_id, ...)`).
Архитектурно честнее, но `self.current_session` используется ~75 раз в пяти миксинах —
большой рефакторинг с риском поломать FSM, ветвление и компрессию. Не стоит того.

**Почему безопасно по БД:** `jarvis_session.py` открывает новое SQLite-соединение
на каждую операцию (`with sqlite3.connect(...)`) — межпоточных проблем с БД почти нет.

## Изменения по файлам

### 1. `webui/app.py` — основная работа

- Реестр агентов + фабрика `get_agent(session_id)`: лениво создаёт `JarvisAgent`
  и делает `switch_session(id)` (восстановление состояния из БД уже реализовано).
- Все stateful-эндпоинты принимают `session_id`: `/api/chat`, `/api/settings` (GET/POST),
  `/api/stats`, `/api/mcp*`. Удобная форма — `/api/sessions/<id>/chat` и т.п.
- `GET /api/sessions/<id>/messages` — убрать проверку «только текущая сессия».
- `POST /api/sessions/<id>/switch` — упразднить (или оставить no-op для совместимости).
- Delete сессии — выкидывать агента из реестра.
- Per-agent `threading.Lock`: параллельные сообщения в один чат сериализуются,
  разные чаты идут параллельно.

### 2. `agents/jarvis_session.py` — маленькая правка + миграция

- Новые колонки в `sessions`: `model`, `temperature`, `max_tokens`
  (`ALTER TABLE` в `try/except sqlite3.OperationalError`, как принято).
  Сохранять при изменении настроек, восстанавливать в `_load_session`.
- `MODEL_PROVIDERS` при восстановлении модели решает, какой `base_url`/`api_key` ставить.
  Карту перенести из `app.py` в общедоступное место (избежать циклического импорта).

### 3. `webui/static/script.js` — параллельный UX

- `currentSessionId` уже есть — слать его во все запросы.
- Убрать глобальную блокировку кнопки отправки; вместо неё карта `pending[sessionId]`.
- Ответ пришёл → рендерить, только если пользователь всё ещё смотрит эту сессию;
  иначе пометить сессию в сайдбаре («⏳» → готово).
- Settings-панель при переключении чата перечитывает настройки выбранной сессии.

### 4. Не трогаем

`jarvis.py`, миксины (кроме п.2), FSM, инварианты, RAG.

## Порядок реализации

1. Миграция БД + сохранение/восстановление model/temperature/max_tokens per-session.
2. Реестр агентов и перевод эндпоинтов на `session_id`
   (совместимость: без `session_id` — поведение как раньше).
3. Локи и проверка гонок (два чата одновременно с облачным LLM).
4. Фронтенд: pending per-session, свободное переключение.
5. Проверка.
6. Обновление документации.

## Риски / открытые места

- **Память процесса:** N агентов = N историй в RAM. Для домашнего использования
  несущественно; при желании — лениво выгружать неактивных.
- **MCP:** у каждого агента свой `mcp_manager` → каждый чат держит свои подключения
  к MCP-серверам. Работает, но подключений больше. Пока принимаем.
- **Профили (long-term memory):** Markdown-файлы общие; одновременная запись из двух
  чатов может конфликтовать — низкий риск, можно прикрыть глобальным локом на запись.
