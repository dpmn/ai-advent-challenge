## Что сделано

Кейс: RAG-ответы по базе знаний проекта на локальной модели (day-28).

**Диагноз (из логов ollama serve, `ollama-serve-log-sample.txt`):** сервер сконфигурирован
на контекст 32768 (`OLLAMA_CONTEXT_LENGTH`), KV-cache 1792 MiB не влезал в 6 GiB VRAM →

- `ragger/search.py` — поле `llm_profile` в `RagPipeline`, прокидывание в реранк.
- `agents/jarvis.py` — `_local_llm_profile()`: num_ctx 8192 (единый на все этапы —
  смена num_ctx перегружает модель), temp 0.0, компактный промпт, keep_alive 30m;
  tok/s и load в `last_rag_debug`.
- `webui/app.py` — два локальных кванта в списке моделей: `qwen2.5-coder:7b` (Q4_K_M)
  и `qwen2.5-coder:7b-instruct-q3_K_M`.
- `webui/static/script.js` — tok/s и load в техстроке RAG.
- `week-06/day-29/bench.py` — бенчмарк: вопросы × профили (baseline/optimized) ×
  модели; JSON в `results/`, сводная таблица в stdout.
- `agents/memory/profiles/local-baseline.md`, `local-optimized.md` — профили Jarvis
  для переключения «до/после» прямо в чате: `_local_llm_profile()` читает поле
  `llm_mode` активного профиля (`baseline` → путь day-28 как есть, иначе —
  оптимизированный). Переключение: `/profile local-baseline` / `/profile local-optimized`.
- `ragger/document_loader.py` — `docs/database-schema.md` добавлен в базу знаний

  54 документа, 72 structural-чанка. Вопрос про таблицы БД теперь отвечаем

**Результаты бенчмарка** (5 вопросов, mode=threshold; полные данные в

|---|---|---|---|---|---|

### Сценарий проверки

1. Подними туннель к Ollama (порт 11434) и запусти WebUI: `python3 ./webui/app.py` → открой http://127.0.0.1:5000
2. В Settings выбери модель `qwen2.5-coder:7b (local)`.
3. Отправь: `/rag on` — ожидаемый результат: «RAG-режим включён».
4. Отправь: `/profiles` — ожидаемый результат: список `default`, `local-baseline`, `local-optimized`.

**До оптимизации (baseline):**

5. Отправь: `/profile local-baseline` — «Переключено на профиль: local-baseline».
6. Отправь запрос: "Какие стратегии чанкинга используются в RAG-пайплайне?"
7. Ожидаемый результат: ответ про fixed-size и structural с источниками; **долго (~40–50 с)**; в серой техстроке `provider local`, но **НЕТ полей tok/s и load** — baseline идёт через OpenAI-совместимый /v1 без метрик, контекст серверный (32768), модель не влезает на GPU целиком.

**После оптимизации (optimized):**

8. Отправь: `/profile local-optimized` — «Переключено на профиль: local-optimized».
9. Отправь тот же запрос: "Какие стратегии чанкинга используются в RAG-пайплайне?"
10. Ожидаемый результат: тот же по сути ответ, **заметно быстрее (~25–30 с)**; в техстроке появились **`NN tok/s` и `load NNs`** — метрики из нативного API Ollama. (Первый запрос после смены профиля включает перезагрузку модели под num_ctx 8192 — это видно по `load`.)

**Квант Q3_K_M (влезает на GPU целиком):**

11. В Settings переключи модель на `qwen2.5-coder:7b-instruct-q3_K_M (local)`.
12. Отправь запрос: "Какие этапы проходит State Machine агента?"
13. Ожидаемый результат: ответ с этапами PLANNING, EXECUTION, VALIDATION, DONE, источники и цитаты; в техстроке модель `qwen2.5-coder:7b-instruct-q3_K_M` (первый запрос дольше — загрузка модели).

**Новое в базе знаний + анти-галлюцинации:**

14. Отправь запрос: "Какие таблицы есть в SQLite базе данных jarvis_history и что в них хранится?"
15. Ожидаемый результат: ответ по существу (таблицы sessions, messages и др.), источник `docs/database-schema.md`, confidence high — схема БД добавлена в индекс в этот день.
16. Отправь запрос: "Как задеплоить проект в Kubernetes?"
17. Ожидаемый результат: честное «Я не знаю», confidence none в техстроке — анти-галлюцинации работают и на компактном промпте.

18. (Опционально) В терминале: `python3 week-06/day-29/bench.py --profiles baseline,optimized --questions 2` — сравнение старой и новой конфигурации на живых замерах.

## Выводы

Прогон: baseline-чат (вопрос про чанкинг, в конце — Kubernetes и State Machine) и
optimized-чат (все вопросы сценария), модель Q4_K_M. Лог сервера —
`ollama-serve-log-run.txt`, разбор — субагентом.

### Что работает

- Переключение «до/после» профилями Jarvis подтверждено логом и `ollama ps`:
  baseline — n_ctx 32768, 18/29 слоёв на GPU, 7.9 GB, 47%/53% CPU/GPU, keep_alive 5m;
  optimized — n_ctx 8192, 24/29 слоёв, 5.4 GB, 21%/79%, keep_alive 30m (наш параметр дошёл).
- Скорость генерации (decode): baseline 2.5 t/s → optimized 4.5–10 t/s (в 2–4 раза);
  prompt eval 267–460 → 583–590 t/s. Латентности запросов: baseline 57 с / 2м06с / 1м11с / 1м06с,
  optimized 38–74 с на сопоставимых вопросах.
- Вопрос про таблицы БД отвечается по `docs/database-schema.md` (добавлен в индекс в этот день),
  confidence high. OOD-вопрос про Kubernetes — честное «Я не знаю» за секунды (6.3 с в baseline).
- Метрики `tok/s` и `load` в техстроке есть только у optimized (нативный API), у baseline их нет —
  наглядная разница для видео.

### Что не работает / требует доработки

- Q4_K_M даже при num_ctx 8192 не влезает на GPU целиком: 24/29 слоёв (79%). 100% GPU
  даёт только Q3_K_M (по бенчмарку), но в этом прогоне Q3 не запускался —
  шаги сценария с Q3_K_M остались непоказанными.
- Абсолютные скорости ниже бенчмарка (4.5–10 t/s против 11–12): запись видео и браузер грузят
  ту же машину; в логе — таймауты GPU discovery watchdog и host memory pressure.
  Загадка низких tok/s при 100% GPU не закрыта — nvidia-smi под нагрузкой не снимали.
- В baseline модель на 32k не уживается с эмбеддером (прогноз 6.1 GiB > 4.7 GiB доступных) —
  взаимные вытеснения и перезагрузки по 40–57 с. Эмбеддер nomic перезагружался 4 раза:
  эмбеддинг запроса стоил то 0.1–0.3 с (резидентный), то 6–11 с (после вытеснения).
  Возможная доработка — keep_alive и для эмбеддера.

### Замечания

- Расплывчатая формулировка «какие таблицы в базе данных проекта» ретривится плохо
  (nomic даёт плоские скоры 0.66–0.74 по всей базе), точная —
  «...SQLite базе данных jarvis_history...» — 0.87. Локальный RAG чувствительнее
  облачного к формулировке запроса.
- Самый долгий optimized-ответ — 2м58с: на вопрос про MCP модель нагенерила 932 токена,
  почти упёршись в num_predict 1024. Кандидат на ужесточение лимита или промпта.
- Смена профиля baseline↔optimized меняет num_ctx — это полная перезагрузка модели
  (десятки секунд), профили стоит переключать редко.
