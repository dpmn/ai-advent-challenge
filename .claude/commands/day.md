# /day — цикл выполнения задания дня

Полный процесс работы над заданием дня. Есть три пользовательских ворот (шаги 2→3, 3→4, 6):
без явной отмашки за ворота не проходишь.

**Главное правило: никакого кода до шага 4.** Фазы «Обсуждение» и «Планирование» — только текст.
Не пиши, не редактируй файлы, не запускай реализацию, пока не получишь явную отмашку на шаге 3→4.

## Порядок действий

1. **Контекст.** Вызови субагент `task-initializer` (Agent tool, subagent_type: task-initializer) —
   он прочитает `docs/progress.md`, лекцию недели, README предыдущего дня и вернёт структурированный контекст.

2. **Обсуждение.** Разбери задание и теорию: что делаем, зачем, как это связано с лекцией недели.
   Уточни непонятное вопросами. **Никакого кода, никакого плана.** Только разбор сути.
   - **⏸ Ворота.** Не переходи к планированию, пока пользователь явно не даст отмашку
     («обсудили», «давай план», «ок, планируй» и т.п.). Дождись её.

3. **Планирование.** Только после отмашки на шаге 2. Составь план реализации: какие файлы,
   что меняем, в каком порядке. Задавай вопросы, корректируй план по фидбэку. **Всё ещё никакого кода.**
   - **⏸ Ворота.** Не начинай реализацию, пока пользователь явно не скажет
     («давай делай», «реализуй», «погнали» и т.п.). Дождись явной отмашки.

4. **Реализация.** Только после явной отмашки на шаге 3.
   - Если правишь агента (`agents/`) — сначала загрузи skill `backend-rules`.
   - Если правишь интерфейс (`webui/`) — сначала загрузи skill `webui-rules`.
   - Если правишь docent (`docent/`) — сначала загрузи skill `docent-rules`.
   - Пиши код по конвенциям из skill. Docstring у всех публичных классов/методов/функций.

5. **Минимальная проверка.** Запусти `python3 ./webui/app.py`, проверь через браузер
   (http://127.0.0.1:5000) или curl. Проверяй только функциональность задания, не UI.

6. **README дня.** Запиши в `week-XX/day-YY/README.md`, какие файлы и что менял (кратко).
   Раздел **«Задание» не редактируй** — он неприкосновенен.

7. **Сценарий проверки.** Допиши в README дня раздел «Сценарий проверки» (правила ниже).

8. **⏸ Пауза.** Сообщи пользователю, что готово к проверке. Он снимет видео, прогонит сценарий
   и пришлёт результаты. Дождись результатов, не продолжай сам.

9. **Выводы.** Получив результаты — допиши в README дня раздел «Выводы» (правила ниже).

10. **Синхронизация доков.** Вызови субагент `docs-sync` (Agent tool, subagent_type: docs-sync)
    коротким промптом (например: «Синхронизируй документацию после дня N»). Не сужай задачу вручную —
    docs-sync сам пройдёт все 6 шагов (progress.md, CLAUDE.md-дерево, database-schema, skills).

## Правила: «Сценарий проверки» (шаг 7)

Сценарий проверки для видео. Пользователь выполняет его шаг за шагом, показывая работу агента через WebUI.

- Проверяем только функциональность задания. Проверки UI не нужны.
- **Никаких абстракций.** Конкретные запросы, конкретные ожидания.
- Сценарий — не скрипт, а текстовые инструкции для человека.
- Шаги выполнимы в WebUI (http://127.0.0.1:5000).
- Если для проверки нужно написать N сообщений — слэш-команды за сообщения не считаются.

Формат:
```
### Сценарий проверки

1. Открой http://127.0.0.1:5000
2. Отправь запрос: "..." (конкретный текст)
3. Ожидаемый результат: ...
4. Проверь, что в ответе есть: ...
```

## Правила: «Выводы» (шаг 9)

Прими результаты проверки от пользователя, сравни с ожидаемым поведением из README (что сделано,
что ожидалось, сценарий проверки). Допиши раздел «Выводы» **после** существующего содержания
(раздел «Задание» **не трогай**).

Формат:
```
## Выводы

### Что работает
- ...

### Что не работает / требует доработки
- ...

### Замечания
- ...
```

Без воды. Только анализ фактов.
