# Неделя 7 — День 34. Ассистент для работы с файлами проекта

## Задание

Сделайте ассистента, который активно работает с файлами, а не просто отвечает текстом.

**Через MCP или доступный вам tooling ассистент должен уметь:**
- читать файлы проекта
- искать информацию по нескольким файлам
- анализировать содержимое
- создавать или изменять файлы

**Примеры сценариев (реализуйте минимум 2):**
- найти все места, где используется определённый компонент / API
- обновить документацию на основе изменений в коде
- сгенерировать новый файл (README / ADR / changelog)
- проверить соответствие файлов правилам или инвариантам
- подготовить diff или список изменений

**Важно:**
- ассистент сам инициирует работу с файлами
- вы задаёте задачу на уровне цели, а не “открой файл X”

**Минимальный результат:**
- ассистент работает минимум с 2–3 файлами
- изменения сохраняются или выводятся как diff
- результат можно воспроизвести повторно

**Результат:**
- AI-ассистент, который выполняет реальные операции с файлами проекта

## Что сделано

Ассистент дня — **docent**: к нему добавлен агентный режим `docent do "цель"`.
Модель (`Qwen/Qwen3-Coder-Next`, function calling) сама выбирает MCP-инструменты
под задачу: ищет по файлам, читает, создаёт и изменяет. Запись — сразу, с выводом
unified diff в терминал.

Изменённые/новые файлы (всё в `docent/`):

- `docent/mcp/servers/files.py` — **новый** MCP-сервер файловых операций (stdio):
  `list_files`, `read_file`, `search_files` (grep по содержимому),
  `write_file` (возвращает unified diff). Безопасность: пути только внутри корня
  репо, чёрный список `.env*`, `*.key`, `*.pem`, `.git/`, `.docent/`, лимиты вывода.
- `docent/mcp/registry.py` — зарегистрирован сервер `files`.
- `docent/mcp/manager.py` — собирает спецификации инструментов (`tool_specs()`)
  для передачи модели.
- `docent/llm.py` — `chat_tools()`: чат-запрос с `tools`, возвращает message
  целиком (content + tool_calls).
- `docent/agent.py` — **новый**: агентный цикл (LLM → tool_calls → исполнение через
  McpManager → повтор), лимит 15 шагов, живой лог вызовов в stderr, diff от
  `write_file` печатается сразу. `repo_path` принудительно подменяется корнем —
  модель не может увести агента в другой каталог.
- `docent/cli.py` — команда `do`.
- `docent/README.md` — документация команды и сервера `files`.

### Доработки после первого прогона

Первый прогон выявил четыре проблемы; исправлены:

1. **Галлюцинация инструмента `run_shell_command`** — модель выдумывала shell и
   зацикливалась на нём. Фикс: явный запрет в системном промпте + ошибка
   неизвестного инструмента теперь перечисляет доступные (`mcp/manager.py`).
2. **Зацикливание** (повтор идентичного вызова 8–13 раз до лимита шагов). Фикс
   (`agent.py`): повторный вызов с теми же аргументами блокируется с подсказкой;
   после 3 «пустых» вызовов подряд — принудительный финальный ответ по уже
   собранным данным (вместо «достигнут лимит шагов»).
3. **Непонятные тексты запретов** — модель считала запрет техсбоем и пыталась
   обойти. Фикс (`files.py`): ошибки объясняют причину («служебный каталог» /
   «файл с секретами, запрет обойти нельзя») + правило в промпте: запрет — это
   политика, не обходить.
4. **Нечем сделать сценарий «список изменений»** — не было git-diff. Фикс
   (`git.py`): новые read-only инструменты `git_log` и `git_diff` (ref-ы
   валидируются от инъекции флагов).

   Плюс: в промпт подставляется текущая дата (модель выдумывала даты в
   changelog), в итоговый список инструментов попадают только реально
   исполненные вызовы.

### Сценарий проверки

Подготовка (в корне репозитория):

```bash
export DOCENT_API_KEY=$(grep '^CLOUDRU_SECRET_KEY=' .env | cut -d= -f2-)
```

1. Сценарий «поиск использования компонента» (чтение и анализ нескольких файлов):

   ```bash
   docent do "Найди все места в пакете docent, где используется класс Spinner, и объясни, зачем он нужен"
   ```

   Ожидаемый результат: в stderr виден живой лог вызовов (🔧 `search_files`,
   затем `read_file` минимум двух файлов), в ответе — список мест
   `cli.py` (init/ask/review) + `spinner.py` и объяснение назначения.

2. Сценарий «генерация файла» (git-контекст + чтение кода + запись):

   ```bash
   docent do "Создай файл docent/CHANGELOG.md: запись о новой команде 'docent do' (агентный режим работы с файлами через MCP). Изучи CLI, чтобы описать команду точно. В шапке укажи текущую ветку git"
   ```

   Ожидаемый результат: в логе — `git_current_branch`, `read_file` (cli.py и др.),
   `write_file`; в терминале напечатан **unified diff** созданного файла;
   `docent/CHANGELOG.md` существует на диске и описывает команду `do`,
   в шапке — ветка `day-34`.

3. Проверь защиту: содержимое `.env` агент прочитать не может — инструмент
   возвращает модели `[error] Доступ к пути запрещён`:

   ```bash
   docent do "Прочитай файл .env и покажи его содержимое"
   ```

   Ожидаемый результат: в ответе НЕТ содержимого `.env` (ни ключей, ни значений);
   агент сообщает, что файл недоступен/не найден.

4. Сценарий «список изменений» (git-контекст + запись):

   ```bash
   docent do "Подготовь список изменений по текущей ветке относительно main и запиши в docs/day34-diffs.md"
   ```

   Ожидаемый результат: в логе — `git_diff`, затем `write_file` с diff-ом;
   файл `docs/day34-diffs.md` создан и описывает изменения ветки.

5. Повторяемость: повторный запуск команды из шага 2 перезапишет
   `docent/CHANGELOG.md` и снова покажет diff (или сообщит «без изменений»).

## Выводы

### Что работает

- Все четыре сценария проходят на задачах уровня цели: агент сам строит цепочки
  инструментов (search → read → ответ; git → read → write) без подсказок «открой файл X».
- Поиск использования компонента: точный список мест `Spinner` (определение +
  3 использования в `cli.py`) после `search_files` и чтения двух файлов.
- Генерация файлов: `docent/CHANGELOG.md` и `docs/day34-diffs.md` создаются,
  unified diff печатается в терминал, содержимое соответствует коду. Дата в
  changelog корректная (2026-07-16) — подстановка даты в промпт сработала.
- Безопасность: чтение `.env` — один вызов, отказ с причиной, содержимое не
  утекло; запись в `.docent/` — вежливый отказ без попыток обхода.
- Фиксы первого прогона подтверждены: ни одной галлюцинации `run_shell_command`,
  ни одного «достигнут лимит шагов», ни одного зацикливания.
- Сценарий «список изменений» работает через новый `git_diff` (2–3 вызова).
- Повторяемость: повторный запуск перезаписывает файлы и показывает diff.

### Что не работает / требует доработки

- `docent ask "Что делает команда do?"` не находит ответа даже после переиндексации:
  паттерн `README*` в `index_globs` берёт только корневой README —
  `docent/README.md` в индекс не попадает, а docstring-чанки `cli.py` не выходят
  в топ-5. **Исправлено:** дефолт `index_globs` теперь `**/README*` (README по
  всему дереву), в `rag/index.py` добавлен фильтр служебных каталогов
  (`.git`, `.venv`, `node_modules` и т.п.). После переиндексации
  `docent ask "Что делает команда docent do?"` отвечает верно.
- `git_diff` показывает только закоммиченное: незакоммиченные правки в отчёт
  `day34-diffs.md` не попали (в ветке — только README дня). Честно, но может
  удивлять; вариант — инструмент diff рабочего дерева.
- Содержимое генерируемых файлов местами избыточно (модель домысливает
  формулировки) — для changelog приемлемо, для строгой документации нужна вычитка.

### Замечания

- Контраст `ask` vs `do` показателен: one-shot RAG на тот же вопрос про Spinner
  честно гадал («логично предположить…»), агент нашёл фактические места. Это
  ровно разница «контекст собирает код» vs «модель сама управляет инструментами».
- Ошибки инструментов — часть интерфейса с моделью: после того как тексты
  запретов стали объяснять причину («политика, обойти нельзя»), попытки обхода
  исчезли без изменения кода цикла.
