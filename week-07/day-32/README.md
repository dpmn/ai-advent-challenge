# Неделя 7 — День 32. Автоматизация ревью кода

## Задание

Настройте пайплайн, в котором ассистент анализирует новый PR.

**Ассистент должен:**
- получать diff и изменённые файлы
- использовать RAG (документация + код)
- выдавать текст ревью

**Минимальный результат:**
- пайплайн (например GitHub Action) запускается на PR
- ассистент получает diff
- возвращает:
  - потенциальные баги
  - архитектурные проблемы
  - рекомендации

**Результат:**
- Автоматическое AI-ревью кода

## Что сделано

Нарастили ассистент `docent` (день 31) до пайплайна AI-ревью PR и подключили
реактивный запуск через GitHub Action.

### docent — код в RAG
- `docent/docent/rag/code.py` (новый) — python-чанкер: через `ast` индексируем
  docstring модуля + сигнатуру и docstring каждого class/def (без тела). RAG
  получает «карту» кода без шума реализации. Битые файлы пропускаются.
- `docent/docent/config.py` — новое поле `code_globs` (явный список каталогов:
  `agents/`, `ragger/`, `docent/`, `mcp_servers/`, `webui/`).
- `docent/docent/rag/index.py` — `build` диспетчеризует по расширению:
  `.md` → markdown-чанкер, `.py` → python-чанкер.

### docent — команда review (мозг ревью)
- `docent/docent/reviewer.py` (новый) — `review(root, config, diff, changed_files)`:
  RAG-контекст (доки + docstring-и кода) + diff → LLM → текст ревью в трёх секциях
  (потенциальные баги / архитектурные проблемы / рекомендации).
  Production-ready надёжность: retry с backoff, fallback на запасную модель,
  усечение гигантских diff.
- `docent/docent/cli.py` — подкоманда `docent review`: diff из `--diff <файл>`
  или stdin; текст ревью → stdout (пригоден для `gh pr comment`), диагностика
  (контекст, модель) → stderr.

### Реактивный пайплайн
- `.github/workflows/ai-review.yml` (новый) — триггер `on: pull_request`
  (opened/synchronize/reopened). Шаги: checkout → setup-python →
  `pip install ./docent` → `docent init` (индекс на лету) →
  `gh pr diff` → `docent review` → пишет/**обновляет** один комментарий к PR
  (поиск прежнего по маркеру `<!-- docent-ai-review -->`).

## Настройка секрета (нужно один раз)

Action берёт ключ Cloud.ru из GitHub Secrets:

1. Репозиторий на GitHub → **Settings** → **Secrets and variables** → **Actions**.
2. **New repository secret**.
3. Name: `DOCENT_API_KEY`, Value: ключ сервиса Cloud.ru Foundation Models.
4. Save. `GITHUB_TOKEN` добавляется автоматически — настраивать не нужно.

## Сценарий проверки

**Локальная часть (терминал):**

1. Экспортируй ключ: `export DOCENT_API_KEY="<ключ Cloud.ru>"`.
2. Построй индекс: `docent init` — ожидается «Готово: файлов …, чанков …».
3. Сгенерируй diff и прогони ревью:
   `git diff main...HEAD | docent review`
4. Ожидаемый результат: в выводе ровно три markdown-секции —
   «## Потенциальные баги», «## Архитектурные проблемы», «## Рекомендации».
5. Проверь, что в ревью есть ссылки на конкретные изменённые файлы из diff,
   а в конце (stderr) — строка «🤖 Модель: …».

**Реактивная часть (GitHub):**

6. Убедись, что секрет `DOCENT_API_KEY` добавлен (см. выше).
7. Создай Pull Request с этой ветки в `main`.
8. Открой вкладку **Actions** — workflow «AI Code Review» должен запуститься
   автоматически на событие открытия PR.
9. Дождись завершения. Ожидаемый результат: в PR появился комментарий от бота
   с текстом ревью (три секции). При новом пуше в ту же ветку комментарий
   **обновляется**, а не дублируется.

## Выводы

### Что работает
- Реактивный запуск: GitHub Action стартовал на PR и оставил комментарий с
  ревью — весь путь `pull_request` → diff → RAG → LLM → коммент отработал.
- Формат: ревью стабильно выдаётся тремя секциями (баги / архитектура /
  рекомендации) во всех прогонах, локально и в CI.
- RAG по коду: findings ссылаются на конкретные файлы и строки
  (`_cmd_review (cli.py, строка 112)`, `reviewer.py`, `code.py`) — индексация
  docstring-ов и сигнатур даёт модели предметный контекст.
- Вывод чистый: stdout = markdown ревью, диагностика (контекст, модель) в stderr
  — комментарий PR не засоряется.
- Модель `Qwen/Qwen3-Coder-Next` отработала на всех прогонах; retry/fallback не
  понадобились (значит, в бою не проверены).

### Что не работает / требует доработки
- **Качество зависит от содержимого diff.** Прогоны 1–2 ревьюили diff, где менялся
  в основном `docs/progress.md` — модель ушла в претензии к документации, а не к
  коду. Ожидаемо (ревьюим что в diff), но полезность на «не-кодовых» diff низкая.
- **Ложные срабатывания.** В PR-комменте модель заявила, что `_QUERY_DIFF_CHARS`
  «нигде не применяется» — это неверно, константа используется в `reviewer.py`
  при сборке RAG-запроса. Причина — модель видит diff-хунки, а не весь файл.
- **`_signature` (code.py) — наивный счётчик скобок.** Не различает скобки/`:`
  внутри строковых литералов и комментариев — на хитрой сигнатуре может
  оборваться раньше. Реальное ограничение (несколько прогонов это подметили).
- **Усечение diff режет по символам**, без сохранения целостности строк и без
  явного маркера обрезки в тексте (сейчас только приписка `[diff усечён]`).
- **Связанность с провайдером.** `_FALLBACK_MODEL` и `code_globs` захардкожены —
  для другого провайдера/репо потребуют правки (для этого проекта осознанно ок).
- **`index.query` ищет по всему индексу**, не фильтруя по изменённым файлам —
  контекст может быть шире нужного (принято для MVP).

### Замечания
- Атрибуция контекста декоративная (наследие дня 31): в stderr перечислены все
  RAG-попадания, а не реально использованные моделью.
- Часть рекомендаций модели дельные (тесты на `_signature`/`chunk_python`,
  подсказка при пустом diff, `continue-on-error` на шаге ревью) — кандидаты в
  бэклог, за рамками минимального результата дня.
- Обновление одного комментария по маркеру в CI подтверждается только повторным
  пушем в PR (в рамках проверки был один прогон).

## Улучшения после ревью (Tier 1–3)

По «Выводам» доработали `docent` тремя этапами (покоммитно на `day-32`):

- **Tier 1 — качество.** В промпт кладём полные версии изменённых файлов, а не
  только diff-хунки (убирает ложные «не используется»). RAG отдаёт только
  соседний контекст. Усечение diff — по границе строки с видимым маркером.
- **Tier 2 — корректность.** `_signature` переписан на `ast.unparse` (не ломается
  на скобках/`:` в литералах). Не-кодовый diff (только доки) не гоняем через LLM.
- **Tier 3 — переносимость/устойчивость.** `fallback_model` вынесен в `Config`;
  честная SOURCES-атрибуция (только реально использованный контекст); подсказка
  при пустом diff; `continue-on-error` в Action + guard пустого коммента.
