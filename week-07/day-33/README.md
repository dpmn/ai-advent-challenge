# Неделя 7 — День 33. Ассистент поддержки пользователей

## Задание

Сделайте мини-сервис для поддержки пользователей.

**Ассистент должен:**
- отвечать на вопросы о продукте
- использовать RAG (FAQ, документация)
- учитывать контекст пользователя или тикета

**Через MCP:**
- подключите CRM
- или JSON с пользователями / тикетами

**Пример:**
- «Почему не работает авторизация?»
- ассистент отвечает с учётом данных тикета

**Результат:**
- AI-ассистент для поддержки пользователей

## Реализация

Выдуманный продукт — SaaS-таск-трекер **TaskFlow**. Ассистент — Jarvis + новый MCP-сервер
`support` (порт 8770), объединяющий «CRM» (JSON) и RAG по FAQ продукта.

**Новые файлы (`mcp_servers/support_mcp/`):**
- `faq/faq.md`, `faq/auth-guide.md`, `faq/billing.md` — FAQ и документация TaskFlow
  (авторизация, 403 после смены пароля, токены, тарифы, лимиты, оплата)
- `data/users.json` — 4 пользователя (id, email, тариф, роль)
- `data/tickets.json` — 6 тикетов с историями сообщений, привязаны к пользователям
- `build_index.py` — индексация FAQ в отдельный FAISS-индекс (`data/index/`)
  через пайплайн ragger (chunk_structural → эмбеддинги Cloud.ru → build_index);
  основной индекс ragger не затрагивается
- `server.py` — FastMCP-сервер, инструменты: `get_user(email)`, `list_user_tickets(user_id)`,
  `get_ticket(ticket_id)`, `search_faq(query, top_k)`. Описания инструментов направляют LLM
  на цепочку: профиль → тикеты → тикет → FAQ → ответ

**Изменённые файлы:**
- `agents/mcp/servers.json` — добавлен сервер `support` (http://127.0.0.1:8770/mcp)

Код Jarvis и WebUI не менялся — инструменты подхватываются MCP-менеджером автоматически.

### Сценарий проверки

Подготовка (один раз):
```bash
python3 mcp_servers/support_mcp/server.py --port 8770   # в отдельном терминале
python3 ./webui/app.py                                   # в отдельном терминале
```

1. Открой http://127.0.0.1:5000, создай **новую сессию**.
2. Убедись, что модель — `Qwen/Qwen3-Coder-Next` (tool calling не работает на Qwen3-30B-A3B).
3. Отправь `/mcp on` — в ответе должно быть `support: ok (4 tools)`.
4. Отправь запрос: **«Здравствуйте! Я Иван Иванов, ivanov@example.com. Почему у меня не работает авторизация?»**
5. Ожидаемый результат: ассистент вызывает инструменты `support__get_user`,
   `support__list_user_tickets`, `support__get_ticket`, `support__search_faq`
   (видно в блоке «MCP-инструменты использованы»).
6. Проверь, что в ответе есть: причина — при смене пароля TaskFlow отзывает сессии
   и API-токены (ошибка 403 `token_revoked` из тикета TK-101); решение — войти заново
   и перевыпустить токен в «Настройки → API-токены».
7. Отправь второй запрос: **«Я petrova@example.com. Не приходит письмо для сброса пароля, что делать?»**
8. Ожидаемый результат: ответ с учётом тикета TK-102 и FAQ — проверить спам
   (адрес no-reply@taskflow.app) и упоминание лимита тарифа Free:
   не более 3 запросов сброса пароля в час (она жала 4 раза — упёрлась в лимит).

Примечание: Cloud.ru периодически отвечает `read timeout` / `HTTP 500` на запросы
с tool calling — при ошибке просто повтори то же сообщение.

## Выводы

### Что работает

- Полная цепочка на персональный вопрос: `get_user` → `list_user_tickets` → `get_ticket`
  → `search_faq`. Оба ключевых кейса (TK-101: 403 после смены пароля; TK-102: лимит
  сброса пароля на Free) отвечены точно по FAQ с учётом данных тикета.
- Контекст диалога: на follow-up «какой крайний срок поступления возврата?» агент
  без повторного представления сам выбрал другой тикет пользователя (TK-105)
  и посчитал срок от даты ответа поддержки (15–22 июня).
- Экономность вызовов: на общий вопрос про тарифы агент вызвал только `search_faq`,
  без CRM-инструментов — маршрутизация «персональное vs общее» работает сама,
  без правок промпта Jarvis.
- Ответы обоснованы чанками FAQ, продуктовое поведение не выдумывается.

### Что не работает / требует доработки

- На «аккаунт всё ещё заблокирован» агент открыл только TK-102 и не заглянул
  в закрытый TK-106 «Аккаунт заблокирован» — а там прямо релевантная история.
  При этом категорично заявил «аккаунт не заблокирован», хотя инструмента проверки
  фактической блокировки у него нет. Лечится либо уточнением описаний инструментов
  («смотри и закрытые тикеты»), либо инструментом статуса аккаунта.
- Агент обещает действия, которых у него нет: «я открою новое обращение»,
  «помогу оформить переход», «передам администратору». Нет инструмента
  `create_ticket` — либо добавить, либо запретить такие обещания промптом.
- Cloud.ru нестабилен на tool calling (read timeout, HTTP 500) — ретраев
  на уровне агента нет, пользователь повторяет сообщение вручную.

### Замечания

- MCP-состояние per-session: `/mcp on` нужно в каждой новой сессии — для демо ок,
  для «сервиса поддержки» включение должно быть дефолтом.
- Весь день собран без правок кода Jarvis/WebUI — вся специфика в одном MCP-сервере
  и описаниях его инструментов. Описания инструментов фактически заменили
  системный промпт.
