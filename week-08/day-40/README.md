### Почему харнес переехал с Claude Code на opencode

Первый вариант был честным bash-драйвером: скрипт брал задачу из пула, запускал
`claude -p "/execute-task T-NN"` в отдельной сессии, сам проверял ворота, сам коммитил
или откатывал. Он работал — но цикл жил в скрипте, а не в агенте.

Переехали по двум причинам:

1. **Архитектурная.** По замыслу лекции execution loop — это агент-маршрутизатор, который
   берёт задачи и делегирует их спецагентам, а не внешний скрипт, дёргающий по сессии
   на задачу. Драйвер решал за агента то, что должен решать агент.
2. **Практическая.** Прогон на Claude Code съел **половину сессионного лимита за одну
   задачу** ($2.58, 458 с, 23 хода). На 16 задач в двух прогонах лимита нет и близко.

Модель прогона — бесплатная `opencode/big-pickle`. Это облако, не локалка: локальные модели
по итогам дня 39 в усиление не берём.

Усиление осталось прежним по смыслу: прогон 1 → разбор падений → правка правил и профилей →
прогон 2 на том же пуле с чистого состояния.

### Оркестратор — `.opencode/agent/loop-orchestrator.md`

Примарный агент, который ведёт весь прогон в одной сессии. У него **отключены инструменты
`write`, `edit`, `patch`** — он физически не может писать код, только маршрутизировать.
Это не просьба в промпте, а свойство агента.

Алгоритм на каждую задачу: отметить старт в журнале → прочитать блок задачи → делегировать
субагенту по типу → прогнать ворота самому → коммит → отметить «сделано». Ворота красные —
вернуть задачу тому же субагенту с текстом ошибки, но не больше трёх прогонов ворот на задачу.
Провал одной задачи прогон не останавливает: откат рабочего дерева, запись причины, следующая
задача.

Фазовые ворота `CLAUDE.md` (обсуждение → план → реализация с отмашкой человека) в прогоне
**явно отменены**: спрашивать некого, а каждая задача уже согласована тем, что лежит в пуле.

### Субагенты-исполнители — `.opencode/agent/`

| тип задачи | субагент | мандат |
|---|---|---|
| `bug` | `bug-fix` | воспроизвести → причина → минимальный фикс → регрессионный тест, который краснеет до фикса |
| `test` | `test-writer` | только `*_test.go`; найденный баг описать, не чинить |
| `feature` | `feature-builder` | дизайн в 3–5 строк, потом минимальный код + тесты |
| `refactor` | `refactorer` | поведение не меняется, существующие тесты зелёные **без правок в тестах** |
| `docs` | `docs-writer` | каждое утверждение сверено с кодом; код не трогает |

`feature-builder` и `refactorer` — новые. В варианте на Claude Code фичи и рефакторинг делал
сам оркестратор (`go-architect` только проектировал), а теперь оркестратор этого не умеет
по построению — значит, исполнители нужны отдельные.

### Скрипты харнеса — `.opencode/loop/`

- `start-run.sh <N>` — **не гоняет задачи**, только готовит условия: предполётные проверки
  (чистое дерево, нет ветки прогона, есть инструменты), ветка `loop-run-N` от базовой,
  каталог журнала, метаданные прогона — и запускает агента один раз. Цикл внутри агента.
  `LOOP_ONLY="T-01 T-05"` — урезанный прогон для проверки самого харнеса.
- `journal.sh` — журнал на **позиционных аргументах**, а не JSON: слабой модели нечего
  форматировать, ошибиться труднее. Время ставит скрипт (`date`), а не агент — по нему
  считается длительность задачи.
- `verify-run.sh <N>` — независимая проверка: переключается на каждый коммит ветки прогона
  и гоняет ворота. Нужна именно потому, что цикл ведёт агент: словам «ворота зелёные» веры нет.
- `report.sh <N>` — метрики. `DONE` ставится только при совпадении двух источников: отметка
  оркестратора **и** зелёные ворота на коммите задачи по `verify-run.sh`.

### Разрешения и страховки — `opencode.jsonc`

- `instructions` — правила проекта подключены ссылками на существующие `CLAUDE.md` и
  `.claude/skills/go-style/SKILL.md`. Своей копии правил не держим, чтобы харнесы не разъехались.
- `permission` — `bash` разрешён, но запрещены явно: `sed -i` (правка файлов мимо инструментов),
  `git push` и `gh` (наружу ничего не уходит), `git checkout -b` / `branch` / `reset` / `rebase` /
  `revert` (ветками и историей распоряжается харнес), чтение `.env`.
- Прогон идёт с `--auto` (автоподтверждение инструментов), запреты выше при этом остаются в силе.

### Что меряем

| метрика | откуда |
|---|---|
| задач подряд без вмешательства (**streak**) | до первой задачи без вердикта `DONE` |
| процент выполненных | вердикты: отметка оркестратора + независимая проверка ворот |
| процент прошедших с первого раза | `gate_runs == 1` |
| среднее / медиана времени | таймстемпы журнала (ставит скрипт, не агент) |
| причина падения | причина из журнала + `session.log` прогона |

Причины падений различаем: не понял задачу · нерабочий код · зациклился · нет разрешения ·
не влез в бюджет · внешний сбой.

## Сценарий проверки

Всё выполняется в `/home/development/personal/fridge-chef`. WebUI курса тут ни при чём.

### 0. Подготовка

```bash
cd /home/development/personal/fridge-chef
git checkout execution-loop-opencode
git status --short          # должно быть пусто
for t in opencode jq timeout go git; do command -v $t >/dev/null && echo "ok $t"; done
```

Последняя команда должна показать шесть агентов харнеса — иначе `opencode.jsonc` или
`.opencode/agent/` не подхватились, и прогон запускать бессмысленно.

### 1. Прогон 1 — исходные правила

```bash
bash .opencode/loop/start-run.sh 1
```

Скрипт создаст ветку `loop-run-1`, каталог журнала и запустит агента-оркестратора. Дальше
цикл ведёт агент: 16 задач сверху вниз, по коммиту на выполненную. Вывод дублируется
в `.opencode/runs/loop/run-1/session.log`.

**Не вмешиваться**: не отвечать, не подсказывать, не править файлы во время прогона.
Прервать целиком — `Ctrl-C` (тогда прогон в зачёт не идёт).

Ориентир по времени неизвестен: на сухом прогоне мелкая задача заняла 89 секунд, но это
одна точка. Общий потолок — 6 часов (`RUN_TIMEOUT`).

### 2. Независимая проверка ворот

```bash
bash .opencode/loop/verify-run.sh 1
```

Переключается на каждый коммит прогона и гоняет `go build`/`vet`/`gofmt`/`test`. Без этого
шага отчёт помечает вердикты как непроверенные — метрика будет со слов агента.

### 3. Отчёт

```bash
bash .opencode/loop/report.sh 1
```

Таблица «задача → тип → субагент → вердикт → время → прогонов ворот → коммит → причина»
и метрики. Файл: `.opencode/runs/loop/run-1/report.md`, копия для коммита —
`docs/loop/runs/run-1/`.

Прислать `report.md` — дальше разбираю падения и правлю правила и профили.

### 4. Прогон 2 — после правки правил

Запускается **после** того, как я закоммичу правки харнеса в `execution-loop-opencode`:

```bash
git checkout execution-loop-opencode && git status --short
bash .opencode/loop/start-run.sh 2
bash .opencode/loop/verify-run.sh 2
bash .opencode/loop/report.sh 2
```

Пул тот же, ветка отводится от обновлённой базовой, состояние чистое. Сравнение двух
`report.md` (в первую очередь streak) — результат дня.

### Если нужно перезапустить прогон с тем же номером

```bash

rm -rf .opencode/runs/loop/run-1
```

Харнес намеренно отказывается писать поверх существующей ветки или журнала — чтобы случайно

### ¹ Дефект честности, который вылёз в прогоне 2

прогона 2 от `start T-14` сразу `done T-14 … 1` без единого `go build`; всего 15 запусков ворот на

именно так метрика «с первого раза» получает одну ячейку **на веру, а не по факту**. Поймала это
только независимая проверка — принцип «агенту на слово не верим» окупился второй раз.

Структурная заплатка (если ужесточать дальше): `journal.sh done` должен требовать доказательство —
хеш последнего gate-запуска, — иначе `done` не принимается. Тогда пропуск ворот стал бы FAILED,
а не тихо зачтённым DONE.

### Сравнение облако vs локальная модель

Задание просит прогнать тот же пул на локальной модели. **Не делали сознательно:** день 39 показал,
что доступные локальные модели кодоген не тянут (см. `week-08/day-39`). Прогонять их по 16 задач,
зная исход, — время в мусор. Сравнение дня — не «облако vs локалка», а «платный Claude Code + драйвер»
против «бесплатная модель + агент-оркестратор»: одна задача T-11 на opus обошлась в 502 с и `$2.91`,
та же T-11 на `big-pickle` — 87–167 с и `$0`, при более аккуратном диффе.
