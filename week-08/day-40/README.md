# Неделя 8 — День 40. Execution Loop: кто дольше продержится без паузы

## Задание

Подготовьте пул задач:
- заведите 15–20 задач в трекере (GitHub Issues / Linear / Notion / даже текстовый файл)
- микс: баги, мелкие фичи, рефакторинг, недостающие тесты, документация 
- каждая задача — понятная, с чётким критерием "сделано / не сделано"

Запустите ассистента в режиме execution loop:
- ассистент берёт задачу из трекера → выполняет → коммитит → берёт следующую 
- всё автономно — вы не вмешиваетесь, не подсказываете, не правите промпт между задачами 
- ассистент сам выбирает профиль (Bug Fix / Research / фича) на основе задачи

Зафиксируйте метрики:
- сколько задач выполнено подряд без вашего вмешательства 
- на какой задаче сломался и почему (не понял контекст / сгенерировал нерабочий код / зациклился) 
- среднее время на задачу 
- процент задач, которые прошли с первого раза

Усиление:
- доработайте правила / профили по результатам падений и запустите loop заново
- сравните: первый прогон vs второй — насколько дольше продержался 
- попробуйте тот же пул на локальной модели — сколько задач вытянет она

Результат:
- Пул из 15–20 задач + лог выполнения (задача → результат → время) + метрика "сколько подряд без паузы" в двух прогонах + сравнение облако vs локальная модель

## Что сделано

Код и харнес — в репо [fridge-chef](https://github.com/dpmn/fridge-chef), ветка `execution-loop`
(от неё отводятся ветки прогонов `loop-run-1` / `loop-run-2`). Локально:
`/home/development/personal/fridge-chef`.

Локальную модель в усиление не берём (решение по итогам дня 39: локалка не тянет кодогенерацию).
Усиление — два облачных прогона: прогон 1 → разбор падений → правка правил и профилей → прогон 2
на том же пуле с чистого состояния.

### Пул задач — `docs/tasks/pool.md`

15 задач по **реальному** инвентарю репозитория, не придуманных под удобство агента: 3 бага,
3 фичи, 4 рефакторинга, 3 теста, 2 доки. У каждой — файлы, суть со ссылкой `файл:строка`
и критерий готовности, проверяемый командой.

Часть задач взята из уже известных дыр: обрезка ответа провайдера по байтам вместо рун
(бьёт кириллицу), отзыв на несуществующий `recipe_id`, инструкции в поле продуктов доходят
до LLM (F7 roadmap), `architecture.md` описывает нереализованное как существующее.

Файл иммутабелен: статусы прогона в него не пишутся, они идут в журнал. Поэтому один и тот же
пул гоняется дважды без сброса руками.

### Команда задачи — `.claude/commands/execute-task.md`

Одна задача = один запуск = одна сессия. Внутри: прочитать блок задачи из пула → выбрать профиль
по её типу (`bug` → `bug-fix`, `test` → `test-writer`, `feature` → `go-architect` + `go-reviewer`,
`refactor` → `go-reviewer`, `docs` → сам) → сделать → ворота → коммит → строка в журнале.

Ключевой момент: `CLAUDE.md` репозитория требует три фазы с отмашкой человека — в этой команде
они **явно отменены**. В headless-режиме спрашивать некого, а задача уже согласована тем, что
лежит в пуле. Без этой отмены агент встал бы на первой же задаче с вопросом «можно приступать?».

### Драйвер и отчёт — `.claude/loop/`

`run-loop.sh` создаёт ветку прогона от `execution-loop` и гоняет задачи по порядку:

```
timeout 900 claude -p "/execute-task T-XX" --model opus \
  --permission-mode acceptEdits --strict-mcp-config --output-format json
```

После каждой задачи драйвер **сам** прогоняет ворота (`go build`/`go vet`/`gofmt -l`/`go test`)
и ставит вердикт независимо от самоотчёта агента: `DONE` только если сошлось всё сразу — код
выхода 0, агент отчитался `DONE`, коммит появился, ворота зелёные. Иначе `FAILED` и откат
к состоянию до задачи (`git reset --hard <head_before>` + `git clean -fd`), прогон идёт дальше.

`report.sh` считает метрики: **streak** (задач подряд до первого падения), доля выполненных,
доля прошедших с первого раза (ворота зелёные с первого прогона), среднее/медиана/максимум
времени, разбор причин падений. Отчёт копируется в `docs/loop/runs/run-N/` как артефакт в гите.

### Страховки автономности

- `.claude/settings.json` — разрешения расширены под автономную работу: правка `internal/**`,
  `cmd/**`, `docs/**`, `README.md`, `.env.example`, `git add`/`commit`, запись в журнал.
  **Каждый отказ разрешения в прогоне считается дефектом харнеса, а не агента** — в headless
  агент видит отказ и начинает выкручиваться, метрика портится.
- `.claude/hooks/guard-secrets.sh` — перенесён из репо курса: блокирует `git commit`, если
  в индексе секреты. Автономный агент с правом коммита без этой страховки — плохая идея.
- `.claude/hooks/guard-loop.sh` — во время прогона (когда задана `LOOP_RUN_DIR`) запрещает
  правку `docs/tasks/pool.md` и `.claude/**`. Агент, переписывающий себе задачу или выдающий
  себе разрешения, обесценивает метрику. В обычной сессии разработки харнеса хук молчит.
- Журнал прогона лежит в `.claude/runs/loop/run-N/` — вне гита, поэтому откат рабочего дерева
  его не стирает.
- `--strict-mcp-config` в драйвере: без него headless-сессия упрётся в подтверждение
  MCP-сервера `playwright` из `.mcp.json`.

### Что меряем

| метрика | откуда |
|---|---|
| задач подряд без вмешательства (**streak**) | вердикты драйвера, до первого `FAILED` |
| процент выполненных | вердикты драйвера |
| процент прошедших с первого раза | `gate_runs == 1` в самоотчёте, сверяется с логом сессии |
| среднее / медиана времени | замер драйвера (`wall_sec`), не самоотчёт |
| причина падения | вердикт драйвера + разбор `~/.claude/projects/…/<session_id>.jsonl` |

Причины падений различаем: не понял задачу · нерабочий код · зациклился · нет разрешения ·
не влез в бюджет · внешний сбой.

### Сухой прогон харнеса (до зачётных прогонов)

Одна задача через драйвер, ветка `loop-run-smoke` (удалена после проверки):

## Сценарий проверки

Всё выполняется в `/home/development/personal/fridge-chef`. WebUI курса тут ни при чём.

### 0. Подготовка

```bash
cd /home/development/personal/fridge-chef
git checkout execution-loop
git status --short          # должно быть пусто
for t in claude jq timeout go git; do command -v $t >/dev/null && echo "ok $t"; done
```

Дерево грязное или ветка другая — драйвер откажется стартовать, это задумано.

### 1. Прогон 1 — исходные правила

```bash
bash .claude/loop/run-loop.sh 1
```

Идёт **~2–3.5 часа** (15 задач, потолок 15 минут на задачу), ориентировочно **$30–45**.
Драйвер печатает по строке на задачу: `DONE 214с a3f91c2` или `FAILED 900с — таймаут 900с`.

Дешевле — `LOOP_MODEL=sonnet bash .claude/loop/run-loop.sh 1`, но учти: профили `bug-fix`,
`test-writer` и `go-architect` закреплены за `opus` во фронтматтере, так что смена модели
затронет только оркестратора задачи, а не исполнителей. Для сравнимости прогонов 1 и 2
модель должна быть одна и та же.

**Не вмешиваться**: не отвечать на вопросы, не подсказывать, не править файлы во время прогона.
Смысл замера именно в этом. Прервать целиком — `Ctrl-C` (тогда прогон в зачёт не идёт).

Что должно быть видно по ходу:
- ни одного запроса разрешений (headless — их некому подтверждать; появились в логе отказы,
  значит дефект харнеса, это материал для правки перед прогоном 2);
- на каждой `DONE`-задаче — свой коммит `T-XX: …`.

### 2. Отчёт прогона 1

```bash
bash .claude/loop/report.sh 1
```

Печатает и сохраняет таблицу «задача → тип → профиль → вердикт → время → прогонов ворот →
коммит → причина» и метрики. Файл: `.claude/runs/loop/run-1/report.md`, копия для коммита —
`docs/loop/runs/run-1/`.

Прислать `report.md` — дальше разбираю логи сессий, ищу причины падений и правлю правила/профили.

### 3. Независимая проверка результата (не доверяя отчёту)

```bash
git checkout loop-run-1
git log --oneline execution-loop..loop-run-1     # по коммиту на каждую DONE-задачу
go build ./... && go vet ./... && gofmt -l . && go test ./...
```

Ворота должны быть зелёными на верхушке ветки. `gofmt -l .` — пустой вывод.

### 4. Прогон 2 — после правки правил

Запускается **после** того, как я закоммичу правки харнеса в `execution-loop`:

```bash
git checkout execution-loop && git pull --ff-only 2>/dev/null; git status --short
bash .claude/loop/run-loop.sh 2
bash .claude/loop/report.sh 2
```

Пул тот же, ветка отводится от обновлённой `execution-loop`, состояние чистое.
Сравнение двух `report.md` (в первую очередь streak) — результат дня.

### Если нужно перезапустить прогон с тем же номером

```bash
git checkout execution-loop
git branch -D loop-run-1
rm -rf .claude/runs/loop/run-1
```

Драйвер намеренно отказывается писать поверх существующей ветки или журнала — чтобы
случайно не затереть результат, который уже нечем воспроизвести.
