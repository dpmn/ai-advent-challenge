# Неделя 8 — День 36. Rules

## Задание

Проанализируйте свой проект и создайте файл правил:
- .cursorrules / CLAUDE.md / .github/copilot-instructions.md 
- опишите: стек, архитектуру, структуру папок, naming conventions, паттерны которые вы используете 
- используйте: глобальный конфиг, локальный конфиг, субагентов и скиллы

Включите в правила:
- 3–5 примеров хорошего кода из вашего проекта (как вы ХОТИТЕ чтобы писалось) 
- 3–5 антипаттернов (что запрещено: any, console.log в проде, прямые SQL-запросы и т.д.)
- шаблон: как должен выглядеть типичный файл (импорты, структура, экспорты)

Проверьте на боевой задаче:
- дайте ассистенту задачу на новый endpoint / компонент / сервис 
- один промпт — без уточнений и переписок
- оцените результат: скомпилировалось? прошло линтер? соответствует стилю проекта?

Усиление:
- доработайте файл правил по результатам — что ассистент не учёл?
- повторите тот же промпт с обновлёнными правилами 
- зафиксируйте разницу между первой и второй генерацией

Результат:
- Файл правил проекта (v2, после итерации) + скриншоты/диффы двух генераций + список того, что больше всего повлияло на качество

## Подход

Целевой репо — **fridge-chef** (Go, отдельный репозиторий). Этот репо — прокси прогресса.
Правила усиливаем **в fridge-chef**, в skill `.claude/skills/go-style/SKILL.md`: добавляем «мясо» —
3–5 примеров хорошего кода из реального кода проекта, 3–5 антипаттернов (плохо→хорошо), шаблон Go-файла.
`CLAUDE.md` остаётся тонким роутером и делегирует конвенции в `go-style`.

Проверка — одношотовой генерацией нового бэкенд-эндпоинта (без фронта, чтобы сигнал был чисто про Go):
две генерации одним и тем же промптом — на baseline-правилах и на v2 — затем сравнение.

## Сценарий проверки

Механика — две **свежие** сессии Claude Code в репозитории fridge-chef:

1. **gen1 (baseline).** Ветка `mvp-test-1` от `mvp`. Правила не тронуты. Дать одношот-промпт (ниже) целиком,
   без уточнений. Проверить локально (команды ниже). Закоммитить результат одним коммитом.
2. Вернуться сюда → я коммичу **v2** `go-style` в ветку `mvp-test-2` (от `mvp`) отдельным коммитом.
3. **gen2 (v2).** Ветка `mvp-test-2`, **новая** сессия, **тот же** промпт. Проверить локально. Закоммитить.
4. Вернуться → сравнение gen1↔gen2 и выводы.

### Одношот-промпт (дать целиком, без уточнений)

```
Добавь новый HTTP-эндпоинт POST /api/v1/feedback — обратная связь пользователя по готовому рецепту.

Контракт:
- Тело запроса — JSON: recipe_id (string, опционально), rating (int, обязателен, допустимо 1..5),
  comment (string, опционально, не длиннее 1000 символов).
- Битый JSON или rating вне 1..5 → ответ 400 с JSON-ошибкой.
- При успехе: добавить одну запись в append-only JSONL-файл. Путь берётся из переменной окружения
  FEEDBACK_PATH (по умолчанию ./feedback.jsonl). Запись — строка JSON с полями запроса плюс временная
  метка получения (UTC, RFC3339). Ответ — JSON {"status":"ok"}, код 201.
- Эндпоинт покрой тестом.

Больше ничего не меняй.
```

### Локальный запуск и проверка

```bash
# 1. Запуск (нужен .env с LLM_BASE_URL / LLM_API_KEY / LLM_MODEL — уже есть в репо)
go run ./cmd/fridge-chef            # лог: "fridge-chef слушает :8080"

# 2. Успех → ожидание 201, {"status":"ok"}
curl -i -X POST localhost:8080/api/v1/feedback -H 'Content-Type: application/json' \
  -d '{"recipe_id":"r1","rating":5,"comment":"вкусно"}'

# 3. Невалидный rating → 400 с {"error": ...}
curl -i -X POST localhost:8080/api/v1/feedback -H 'Content-Type: application/json' -d '{"rating":9}'

# 4. Битый JSON → 400
curl -i -X POST localhost:8080/api/v1/feedback -H 'Content-Type: application/json' -d 'не json'

# 5. Файл фидбэка — по строке на запрос, с временной меткой
cat ./feedback.jsonl                # или $FEEDBACK_PATH

# 6. Гигиена
go vet ./...
gofmt -l .                          # должно быть пусто
go test ./...                       # зелёный
```

Оценка каждой генерации: собралось? `go vet` чисто? `gofmt -l` пусто? тест есть и зелёный?
стиль совпал с проектом (хелперы `writeJSON`/`writeError`/`decode`, конфиг через `config.Config`,
godoc у exported, без глобалей/`panic`)?

**Гигиена диффа:** `feedback.jsonl` не в `.gitignore`. Если ассистент сам его не добавил — перед коммитом
удали файл (`rm feedback.jsonl`), чтобы рантайм-данные не попали в дифф генерации.

## Выводы

Сравнение двух одношотовых генераций одного промпта (`POST /api/v1/feedback`):
gen1 — ветка `mvp-test-1` (baseline-правила), gen2 — ветка `mvp-test-2` (правила v2, rules-коммит `70722dd`).

### Что работает
- Обе генерации: собрались, `go vet` чисто, `gofmt -l` пусто, `go test ./...` зелёный; функционал идентичен
  (201 на валидный, 400 на невалидный/битый, строка в JSONL).
- HTTP-слой в обеих — эталонный и **одинаковый**: переиспользованы `decode`/`writeError`/`writeJSON`,
  валидация, 201 Created, `utf8.RuneCountInString` для длины comment, godoc у exported, конфиг через
  `config.Config`+env, обёртка ошибок `%w`, без глобалей/`panic`. Это заслуга baseline-прозы — сработала уже на gen1.
- **Оба целевых рычага v2 сработали ровно как предсказано:**
  1. **Гигиена рантайм-данных.** gen2 добавил `/feedback.jsonl` в `.gitignore` и `FEEDBACK_PATH` в `.env.example`; gen1 — нет.
  2. **Имя конструктора.** gen2 → `feedback.New(...)`; gen1 → `feedback.NewStore(...)`.

  ```diff
  # .gitignore — только gen2
  + /feedback.jsonl
  # конструктор
  - func NewStore(path string) *Store   // gen1
  + func New(path string) *Store        // gen2
  ```

### Что не работает / требует доработки
- **Выборка N=1 на условие.** LLM недетерминирована; часть отличий gen2 (`omitempty` на опциональных полях,
  перенос сборки `Entry`+timestamp внутрь `Store.Append`) на правила чисто **не отнести** — это в пределах шума
  одиночного прогона. Для доказательного вывода нужен прогон ×N и учёт только устойчивых различий.
- **«Мясо» (примеры/антипаттерны/шаблон) видимого прироста на сильной модели не дало.** Baseline-проза уже
  кодировала те же конвенции, gen1 их выполнил. Иллюстрации подтверждают поведение, а не поднимают его.

### Что больше всего повлияло на качество (по убыванию)
1. **Снятие двусмысленности правила** (`NewX` → уточнили: `New`, когда пакет строит один тип). Правило было,
   но размытое; gen1 взял допустимую, но не-идиому — gen2 детерминированно исправился.
2. **Закрытие пробела покрытия** (рантайм-данные → `.gitignore`). Правила молчали → gen1 промолчал тоже;
   добавили строку — gen2 закрыл.
3. **Конкретные примеры хорошего кода** — минимальный эффект на этой модели (проза дублировала их смысл).
   Ожидаемо выше на слабых/дешёвых моделях и при росте кодовой базы — ценность как страховка, не как лифт.

**Одной строкой:** на сильной модели правила поднимают качество не иллюстрациями уже-описанного, а снятием
двусмысленности и закрытием пробелов. Примеры — страховой полис, а не рычаг.
