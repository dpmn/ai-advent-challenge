## Подход

Основной сценарий работы — **терминал**, не IDE-плагин. Отсюда связка из двух инструментов:

- **aider** (терминал) — чат и агентный режим. Выбран как единственный из кандидатов, спроектированный
  под слабые модели: правки идут текстовыми search/replace-блоками, а не через function-calling,
  который 7B на коротком окне разваливает; repo map держит контекст маленьким.
- **ProxyAI** (плагин PyCharm) — автокомплит. В терминале автокомплита не существует в принципе:
  FIM-подсказка это редакторская фича, ей некуда рендериться в CLI.

Изначально на роль плагина был выбран **Continue** — привлекал единый декларативный `config.yaml`
на чат и автокомплит. Он не нашёлся в Marketplace: плагин помечен тегом `deprecated`
(`searchable: false` в API маркетплейса), и JetBrains скрывает такие из поиска внутри IDE.
Совместимость у него в порядке (`since=241.0`, без верхней границы), но последний релиз — 1.0.67
от 2026-03-27. Заменён на ProxyAI: 940k загрузок, сборка 3.8.2-261 от 2026-05-27 — ровно под
build 261 (PyCharm 2026.1), Ollama подхватывает автоматически, FIM-шаблоны поддерживает.
Размен: настройки ProxyAI живут в UI IDE, а не в версионируемом файле.

Железо — то же, что в дне 29: Ollama на удалённой машине, порт 11434 через туннель, видеокарта 6 GiB.

**Модели.** Чат и правки — `qwen2.5-coder:7b-instruct-q3_K_M` (проверена в дне 29, единственный
квант, влезающий на GPU целиком). Автокомплит — `qwen2.5-coder:1.5b-base`, скачана в этот день.
Для IDE из них сделаны производные с вшитым окном (`fridge-chat:q3-ctx4k`, `fridge-fim:1.5b-ctx2k`) —
почему, разобрано ниже.

**Задачи для прогона взяты готовые**, чтобы сравнение с облаком было честным, а не «похожим»:
одношот-фича из дня 36 (`POST /api/v1/feedback`, промпт дословно) и баг из дня 37 (не-кулинарный ввод
доезжает до LLM). Ветки прогонов стартуют с **тех же коммитов**, с которых работал облачный ассистент:

| прогон | ветка | база | почему эта база |
|---|---|---|---|
| R1 — генерация фичи | `local-gen` | `70722dd` | `go-style` v2 уже есть, эндпоинта ещё нет; эталон облака — `6397fde` |
| R2 — агентный режим | `local-bugfix` | `acdc14b` | ровно тот коммит, с которого работал профиль `bug-fix` в дне 37 |

## Что сделано

Всё в репозитории [fridge-chef](https://github.com/dpmn/fridge-chef), ветка `local-boost`,
коммит `27101de` (на ветках прогонов — те же файлы, `882f818` и `8a860c8`).

### Файл правил под окно локальной модели

`CONVENTIONS.md` (новый) — сжатая выжимка `CLAUDE.md` + skill `go-style`.

Ключевая находка: **полные правила физически не помещаются в контекст**. Исходники — 21.8 КБ, это
порядка 7–8 тысяч токенов на русском, то есть всё окно целиком, без места под код. Пришлось выкинуть
все примеры кода и шаблон файла, оставив императивы: стек и запрет зависимостей, layout, обработка
ошибок и sentinel'ы, обязательные хелперы пакета `api`, конструктор `New` и запрет глобалей,
док-комменты, требования к тестам, порядок в файле, блок «Запрещено». Замер по факту (`/tokens`
в aider): **880 токенов**.

### Конфиг терминального ассистента

- `.aider.conf.yml` — модель, `read: CONVENTIONS.md` (правила в каждом запросе), `map-tokens: 1024`,
  `auto-commits: false` и `dirty-commits: false` (дифф прогона должен остаться артефактом),
  отключены телеметрия, проверка обновлений и подтягивание URL из промпта.
- `.aider.model.settings.yml` — формат правок и параметры генерации.
- `.aider.model.metadata.json` — `max_input_tokens` / `max_output_tokens`, иначе aider считает
  бюджет по умолчанию и молча переполняет окно.
- `.gitignore` — служебные файлы aider.

**Формат правок пришлось менять по результату живой проверки.** Изначально стоял `diff`
(search/replace-блоки) — он экономит выход и потому выглядел правильным выбором под медленную модель.
На тесте выяснилось, что 7B его не держит: модель выдала SEARCH-блок с пробелами вместо табов,
правка не применилась, aider ушёл в цикл рефлексий, и на третьей попытке модель **снесла существующую
функцию и потеряла импорт**. Два потерянных прогона и минуты впустую.

С `edit_format: whole` тот же файл в 246 строк (`api.go`) правится корректно: +6 строк, остальной код
цел, маршрут зарегистрирован, использован проектный хелпер `writeJSON` — то есть правила из
`CONVENTIONS.md` дошли. Цена — модель переписывает файл целиком: ~2.3k токенов на выход, **2 мин 55 с**
на одну правку. Отсюда `num_predict: 4096`.

Побочно на этом же тесте видно и слабое место: док-коммент модель написала как `// New handler`
вместо русского godoc-комментария с именем функции, хотя это прямое требование правил в контексте.

**Параметры подобраны замером, а не по умолчанию.** Короткий промпт, `num_predict 300`, `temperature 0`:

| num_ctx | доля модели в VRAM | tok/s |
|---|---|---|
| 8192 | 100% | 14.8 |
| 12288 | 89% | 16.8 |
| **16384** | **86%** | **18.0** |
| 20480 | 80% | 16.7 |

Прогноз, что частичный офлоад на CPU обрушит скорость (как в дне 29, где 18/29 слоёв давали 12 tok/s),
**не подтвердился**: до 86% в VRAM штраф не виден вовсе, выигрывает более широкое окно. Взято 16384.
На реалистичном промпте в 2929 токенов: prompt eval 770 tok/s (3.8 с), генерация 16.8 tok/s.

Бюджет контекста при добавленных `internal/api/api.go` и `internal/config/config.go`:
системный промпт 1947 + repo map 1081 + правила 880 + файлы 2980 = **6888 токенов**.
Для сравнения, при первоначальных 8192 свободного места оставалось 3245 токенов — то есть
ни один рабочий файл в окно уже не влезал. Окно поделено как 12288 на вход и 4096 на выход:
формат `whole` требует места под переписанный файл целиком.

### Автокомплит в PyCharm: две производные модели вместо конфига

**Порог сосуществования моделей измерен явно** — он оказался узким местом всей связки.
В IDE на видеокарте должны жить сразу две модели: чат и FIM-модель автокомплита.

| конфигурация | занято в VRAM | результат |
|---|---|---|
| чат @16384 (4.94 GB) + автокомплит (1.11 GB) | 6.05 GB | вытеснение |
| чат @8192 (4.18 GB) + автокомплит (1.11 GB) | 5.29 GB | вытеснение |
| **чат @4096 (3.95 GB) + автокомплит (1.11 GB)** | **5.06 GB** | **обе резидентны** |

Проверено, что дело именно в VRAM, а не в лимите Ollama на число моделей: две мелкие модели
(`1.5b-base` + `nomic-embed-text`) уживаются свободно. Превышение порога стоит перезагрузки
модели (~14 с) на каждом переключении «чат ↔ подсказка».

**Проблема: плагин не умеет задавать `num_ctx`.** В коде ProxyAI фабрика запросов к Ollama
(`OllamaRequestFactory`) — пустой наследник базовой, никаких ollama-специфичных `options` не шлёт.
Значит применяется серверный дефолт, а на этой машине `OLLAMA_CONTEXT_LENGTH` до сих пор **32768**
(он же ломал baseline в дне 29). Проверено запросом без `num_ctx`: модель раздувается до 5.94 GB,
влезает в VRAM лишь на **71%** и вытесняет модель автокомплита.

**Решение — производные модели с вшитым окном**, через `POST /api/create` (не требует ни правки
env на сервере, ни перезапуска Ollama; веса не перекачиваются, создаётся только новый манифест):

| модель | база | вшито |
|---|---|---|
| `fridge-chat:q3-ctx4k` | `qwen2.5-coder:7b-instruct-q3_K_M` | `num_ctx 4096`, `temperature 0`, `top_p 0.9` |
| `fridge-fim:1.5b-ctx2k` | `qwen2.5-coder:1.5b-base` | `num_ctx 2048`, `temperature 0.1`, `top_p 0.9` |

Результат при запросах **без** явного `num_ctx`, то есть ровно так, как шлёт плагин:
обе модели резидентны, каждая на **100%** в VRAM, суммарно **5.05 GB**.

Автокомплиту нужна именно **base**-модель: instruct-варианты не обучены на FIM и в инлайн-подсказках
отвечают текстом вместо кода. 7B в этой роли неприменима арифметически — при ~17 tok/s подсказка
идёт десятки секунд. Замер FIM через туннель: **~100 tok/s, отклик 0.6 с** на короткую подсказку.

Правила проекта в ProxyAI задаются как **персона** (Settings → Tools → ProxyAI → Prompts) — это его
механизм системного промпта. На автокомплит они **не действуют**: FIM это сырое продолжение префикса
и суффикса, системного промпта в этом режиме нет вообще. «Правила в системный промпт» закрывается
для чата — в терминале через `CONVENTIONS.md`, в IDE через персону.

### Отвергнутый вариант: весь день на одном ProxyAI

У ProxyAI есть агентный режим, и по устройству он ложится на дни 36–38 лучше, чем aider:
файл правил `PROXYAI.md` в корне репозитория (аналог `CLAUDE.md`), субагенты с allowlist
инструментов в версионируемом `.proxyai/settings.json` (то же самое, что профили дня 37,
включая структурный запрет через отсутствие инструмента), плюс skills, hooks и откаты по timeline.
Соблазн собрать весь день на одном инструменте был сильный.

**Не взлетело: локальные модели не держат tool-calling.** Агент ProxyAI построен на
koog-agents 0.8.0 — это нативные вызовы функций, текстового фолбэка нет. Если модель не выдаёт
структурный `tool_calls`, агент не выполнит ни одного действия. Замеры:

| модель | что произошло |
|---|---|
| `qwen2.5-coder:7b-instruct-q3_K_M` | вызов выдан **текстом в `content`**, поле `tool_calls` пустое |
| `qwen2.5-coder:7b` (Q4_K_M) | то же самое — дело не в квантовании |
| то же, без system-промпта | то же самое |
| то же, с явным требованием тегов `<tool_call>` | то же самое |
| `qwen3:4b`, ход 1 (простое чтение файла) | **структурный вызов получен**, 57.6 с |
| `qwen3:4b`, ход 2 (правка файла, 2952 токена в промпте) | сжёг весь бюджет вывода на рассуждения, вызова нет |

Про qwen2.5-coder: шаблон модели в Ollama содержит корректную инструкцию «верни json внутри
`<tool_call></tool_call>` без другого текста», и `capabilities` заявляют `tools`. Модель выдаёт
правильный JSON, но без обёртки, поэтому парсер Ollama его не видит. Это слабость самой модели —
она заточена под генерацию кода, а не под протокол вызовов.

Про qwen3:4b — она протокол держит, но не сходится. На ходу правки: 191 с, 2048 токенов вывода
целиком ушли в рассуждения на английском, вызов `edit_file` так и не прозвучал. Воспроизведено
и с `think: true` (2048 токенов рассуждений, пустой ответ), и с `think: false`, и с прямым
указанием «не рассуждай долго, сразу вызывай инструмент». При 18 tok/s каждая такая попытка
стоит 2–4 минуты, а агентная задача уровня дня 37 требует полутора-двух десятков ходов.

Отсюда и подтверждение исходного выбора: **aider не использует tool-calling вообще** — правки идут
текстом в формате `whole`, и слабой модели нужно попасть не в протокол, а просто в синтаксис Go.

### R1 — результат: провал за три попытки

Ветка `local-gen`, база `70722dd` — тот же коммит, с которого работал облачный ассистент.
Промпт дня 36 дословно, без уточнений. Логи всех трёх попыток — в `logs/`.

| попытка | файлы в контексте | время | что произошло |
|---|---|---|---|
| 1 | `api.go`, `config.go`, `main.go` | 5 мин 28 с | ответ содержал правки `api.go` **и** `api_test.go`, но тестового файла не было в контексте — aider отбрасывает такой ответ целиком и просит повторить. На повторе модель забыла про `api.go` и переписала только тест, **удалив 166 строк существующих тестов** |
| 2 | + `api_test.go` | 26 мин, снята вручную | модель усекла путь: выдала заголовок `api/api.go` вместо `internal/api/api.go`. aider создал новые файлы в несуществующем каталоге `api/`, настоящий код не тронут. Оба хода упёрлись в потолок вывода 6144 токена, цикл не сходился |
| 3 | `api.go`, `api_test.go` | 8 мин 19 с | правки применены по верным путям, +87 строк, **0 удалений** — существующие тесты целы |

Попытка 2 показала важное: в попытке 1 путь был верный, а с ростом контекста модель начала его
усекать. Деградация не от сложности задачи, а от объёма контекста.

**Третья попытка дошла до кода, но провалила критерий:**

```
gofmt -l .   → пусто, ок
go build     → internal/api/api.go:5:2:  "context" imported and not used
                internal/api/api.go:12:2: "path/filepath" imported and not used
go vet       → те же ошибки
go test ./...→ FAIL (build failed) в internal/api и cmd/fridge-chef
```

Диагностика: во временном worktree удалил ровно эти два импорта — код **собрался**, но
`go test ./internal/api/` всё равно упал: `api_test.go:210: статус 201, ожидался 400`.
Модель написала тест, противоречащий её же реализации: кейс «слишком длинный комментарий»
ожидает 400, а комментарий в нём — **100 символов** при лимите 1000. То есть до зелёного
не хватало не одной правки, а двух независимых.

Сверх того, даже если бы собралось и прошло, в коде остаются дефекты:

- **`file.Write(entry)` без `\n`** — записи склеиваются в одну строку, это уже не JSONL,
  а контракт требует «строка JSON» на запись. Функциональный баг против задания.
- `FEEDBACK_PATH` читается через `os.Getenv` прямо в хендлере, мимо пакета `config`,
  где собран весь конфиг проекта.
- Нет пакета `internal/feedback` — вся логика записи инлайном в HTTP-хендлере.
- Нет мьютекса на конкурентную запись в файл.
- Ошибки уходят только клиенту, без `log.Printf` с контекстом, хотя правила требуют обоих.
- `map[string]interface{}` вместо `any`.

Что модель сделала **правильно**: маршрут зарегистрирован method-pattern'ом рядом с остальными,
использованы проектные хелперы `decode`/`writeJSON`/`writeError`, валидация `rating` 1..5 и лимита
комментария на месте, статус 201 и тело `{"status":"ok"}` по контракту, док-коммент на русском
начинается с имени функции, новый тест дописан в конец файла без порчи существующих.
Правила из `CONVENTIONS.md` дошли частично: стиль хендлера — да, структура пакетов и работа
с конфигом — нет.

**Для сравнения — облачный ассистент** на том же коммите и том же промпте: один проход,
9 файлов, 281 добавленная строка, включая отдельный пакет `internal/feedback` со `sync.Mutex`
и 144 строки тестов к нему.

### R2 — результат: провал с первой попытки

Ветка `local-bugfix`, база `acdc14b` — тот же коммит, с которого работал облачный профиль `bug-fix`
дня 37. Тот же симптом без диагноза. Контекст минимальный (`api.go` + `api_test.go`) — конфигурация,
на которой R1 хотя бы не разваливался по путям. Время — **9 мин 6 с**, один ход, правки применены.

Гипотеза, что R2 пойдёт легче R1 из-за меньшего объёма вывода, **не подтвердилась**. Диффа вышло
13 строк, и ни одна из них не по делу:

| критерий дня 37 | результат |
|---|---|
| причина названа верно (нет валидации на пути `normalize` → `generate`) | **нет** — `normalize` вообще не тронут |
| фикс закрывает баг | **нет** — функциональных изменений ноль |
| регрессионный тест падает на старом коде | **нет** — тест закрепляет баг, а не ловит его |
| `gofmt -l .` пусто | **нет** — `internal/api/api.go` |
| `go test ./...` зелёный | **нет** — падает её собственный новый тест |
| `go build`, `go vet` | ок |

Что произошло по факту:

- **Правки в `api.go` — только сломанные отступы.** Модель добавила лишние табы трём строкам внутри
  `if` в `handleFeedback` — хендлере, не имеющем к багу никакого отношения. Ноль функциональных
  изменений, и именно это ловит `gofmt`.
- **Новый тест закрепляет баг.** `TestRecipeInvalidInput` ожидает код **200** и текст «не могу
  обработать запрос», то есть ожидает, что LLM всё-таки вызовется и вежливо откажет. Требование было
  ровно обратное: не-кулинарный ввод не должен доезжать до LLM (ожидается 400). Тест падает —
  но не потому, что поймал баг, а потому что получил 404 вместо своих же 200.
- **Испорчен посторонний проходящий тест.** В `TestSuggest` продукт `"яйца"` заменён на `"яйцо"` —
  мутация теста, не связанного с задачей ничем.

Самое показательное — модель **словами сформулировала верный план**:

> Для решения проблемы с обработкой не-кулинарных запросов и добавления регрессионного теста, нужно:
> 1. Добавить проверку на валидность продуктов перед их передачей в LLM.
> 2. Создать новый тест для проверки этой функциональности.

…после чего выдала диff со сломанными отступами. Разрыв не в понимании задачи, а между планом
и его исполнением: удержать намерение через переписывание файла целиком модель не может.

**Для сравнения — облачный профиль `bug-fix`** на том же коммите: воспроизвёл симптом до правок,
локализовал причину со ссылкой `файл:строка`, дал минимальный фикс, закрыл регрессионным тестом,
падающим на старом коде, и прогнал `go test`/`go vet`/`gofmt`. Со второй итерации профиля — ещё и
с закрытием пути через UI, где фронт режет ввод по запятой.

### Таблица: облако vs локальная модель

Строка про автокомплит заполняется после прогона R3.

| критерий | облачный ассистент | локальная модель |
|---|---|---|
| **Качество кода, R1** (фича) | собралось, тесты зелёные, отдельный пакет `internal/feedback` с мьютексом, 9 файлов / 281 строка | не собралось (2 неиспользуемых импорта); после их снятия падает её же тест; запись без `\n` — не JSONL |
| **Качество кода, R2** (баг) | причина со ссылкой `файл:строка`, минимальный фикс, регрессионный тест падает на старом коде | фикса нет вовсе: сломаны отступы в постороннем хендлере, тест закрепляет баг, испорчен посторонний тест |
| **С первого раза?** | да, оба прогона | нет, ни одного из двух |
| **Скорость** | один проход | R1 — 3 попытки, 40 мин суммарно (5:28 + 26:00 + 8:19); R2 — 9:06. Генерация 17–18 tok/s |
| **Понимание контекста проекта** | полное: структура пакетов, конвенции, инварианты | частичное. Дошло: хелперы `decode`/`writeJSON`/`writeError`, method-pattern, док-комменты на русском. Не дошло: структура пакетов, работа через `config`, мьютекс на конкурентную запись |
| **Устойчивость к объёму контекста** | не наблюдалась | деградирует явно: на 3 файлах путь верный, на 4 — усечён до `api/api.go` |
| **Работа без интернета** | нет, нужен доступ к провайдеру | да — модель на своём железе, стороннего сервиса нет (нужен лишь туннель до своей же машины) |
| **Стоимость** | по токенам провайдера | ноль сверх электричества |

**Для чего локальной модели хватает** (по этим замерам):

- Автокомплит по префиксу и суффиксу — 1.5B-base даёт ~100 tok/s и отклик 0.6 с, это её родная задача.
- Точечная правка в одном файле по внятному описанию: добавить функцию, дописать хендлер по образцу
  соседнего. Проверено отдельно — `handlePing` в `api.go` она сделала корректно, с проектным хелпером.
- Ответы на вопросы по одному-двум открытым файлам (что делает функция, где регистрируются маршруты).

**Где облако незаменимо:**

- Многофайловая фича с новым пакетом: локальная не удержала задачу ни в одной из трёх попыток.
- Агентная работа. Две независимые причины: локальные модели не выдают структурный tool-calling
  (`qwen2.5-coder` — вообще, `qwen3:4b` — не сходится за разумное время), а без него агентные
  фреймворки не работают; и даже в текстовом режиме aider модель не переносит собственный план в дифф.
- Любая задача, где нужно удержать в голове больше 3–4 файлов: деградация по контексту измерена.
- Задачи, где цена ошибки высока: модель дважды портила существующий код молча —
  166 строк тестов в R1 и посторонний тест в R2.

### R1 — генерация фичи одним промптом (задача дня 36)


Внутри aider — `/tokens` (показать бюджет контекста на видео), затем **дословный промпт дня 36**,
целиком, без уточнений и переписок:

```
Добавь новый HTTP-эндпоинт POST /api/v1/feedback — обратная связь пользователя по готовому рецепту.

Контракт:
- Тело запроса — JSON: recipe_id (string, опционально), rating (int, обязателен, допустимо 1..5),
  comment (string, опционально, не длиннее 1000 символов).
- Битый JSON или rating вне 1..5 → ответ 400 с JSON-ошибкой.
- При успехе: добавить одну запись в append-only JSONL-файл. Путь берётся из переменной окружения
  FEEDBACK_PATH (по умолчанию ./feedback.jsonl). Запись — строка JSON с полями запроса плюс временная
  метка получения (UTC, RFC3339). Ответ — JSON {"status":"ok"}, код 201.
- Эндпоинт покрой тестом.

Больше ничего не меняй.
```

Чего ждать по времени: формат правок — `whole`, модель переписывает каждый затронутый файл целиком,
одна правка `api.go` в тесте заняла ~3 минуты. Не пугаться паузы и **не добавлять лишние файлы в чат**
(`/add`) — каждый добавленный файл модель может переписать целиком. Если aider предложит создать новый
файл (`internal/feedback/feedback.go`) — соглашаться.

Засечь время от отправки промпта до окончания правок. Выйти из aider (`/exit`), затем проверка:

```bash
gofmt -l .                          # должно быть пусто
go vet ./...                        # чисто
go build ./...                      # собирается
go test ./...                       # зелёный
git diff --stat                     # что именно тронула модель
```

Живая проверка эндпоинта — как в дне 36:

```bash
go run ./cmd/fridge-chef            # в отдельном терминале
curl -i -X POST localhost:8080/api/v1/feedback -H 'Content-Type: application/json' \
  -d '{"recipe_id":"r1","rating":5,"comment":"вкусно"}'      # 201, {"status":"ok"}
curl -i -X POST localhost:8080/api/v1/feedback -H 'Content-Type: application/json' -d '{"rating":9}'   # 400
curl -i -X POST localhost:8080/api/v1/feedback -H 'Content-Type: application/json' -d 'не json'        # 400
cat ./feedback.jsonl
```

**Важно: если что-то не собралось или тест красный — руками не дочинивать.** Смысл прогона в том,
что модель сделала сама; провал — такой же валидный результат, как успех, и именно он идёт в таблицу.
Правки оставить в рабочем дереве, не коммитить.

### R3 — автокомплит в PyCharm

**Важно: закрыть aider перед этим прогоном.** В aider окно 16384 (4.94 GB), и одновременно
с моделью автокомплита оно в 6 GiB не помещается.

Установка (разово): PyCharm → Settings → Plugins → Marketplace → **ProxyAI** → Install → перезапуск.
(Плагин Continue искать бесполезно — он помечен `deprecated` и скрыт из поиска в IDE.)

Настройка провайдера: **Settings → Tools → ProxyAI → Providers → Ollama (Local)**

1. Host — `http://localhost:11434` (значение по умолчанию, туннель слушает там же).
2. `Refresh Models` — в списке должны появиться `fridge-chat:q3-ctx4k` и `fridge-fim:1.5b-ctx2k`.
3. Включить **Code Completions** (по умолчанию выключены).
4. FIM template — **`CodeQwen2.5`** (значение по умолчанию, оно же верное для нашей модели).
5. Apply.

Модели по фичам: **Settings → Tools → ProxyAI → Models** — там назначение модели на каждую фичу
отдельно. Нужно:

- `CHAT` → `fridge-chat:q3-ctx4k`
- `CODE_COMPLETION` → `fridge-fim:1.5b-ctx2k`

Правила проекта: **Settings → Tools → ProxyAI → Prompts** → добавить персону, вставить текст из
`week-08/day-39/proxyai-persona.md`, сделать её персоной по умолчанию.

Проверка, что обе модели резидентны и каждая целиком на GPU:

```bash
curl -s localhost:11434/api/ps | python3 -c "
import sys,json
for m in json.load(sys.stdin)['models']:
    print(m['name'], 'ctx=', m.get('context_length'), f\"vram={100*m['size_vram']/m['size']:.0f}%\")"
# ожидается: fridge-chat ctx=4096 vram=100%, fridge-fim ctx=2048 vram=100%
```

Дальше — в PyCharm:

1. Открыть `ingestion/` (Python — родной язык для PyCharm), начать печатать функцию,
   дождаться серой инлайн-подсказки, принять по Tab. Повторить на ~5 позициях.
2. Открыть `internal/api/api.go` (Go-плагина в PyCharm нет — проверяем, что FIM работает
   независимо от языковой поддержки IDE). Поставить курсор внутри пустого тела функции,
   дождаться подсказки. Повторить на ~5 позициях. Известная особенность: в стоп-токенах шаблона
   `CodeQwen2.5` есть `package ` и `import `, поэтому у самого верха Go-файла подсказка
   будет обрываться — это не поломка, проверять внутри функций.
3. Открыть панель ProxyAI → чат → спросить что-нибудь по открытому файлу
   (например «что делает handleSuggest?»), убедиться, что персона с правилами применяется.

Фиксируем: задержка до появления подсказки (на глаз/по видео), сколько из ~10 подсказок
оказались осмысленными, были ли перезагрузки модели между чатом и подсказками
(повторить `api/ps` после переключений — обе модели должны остаться резидентными).
