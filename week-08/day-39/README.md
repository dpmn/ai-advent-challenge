### Настройка контекста под железо

Ollama по умолчанию даёт контекст 32768 — на этом железе модель не влезает в VRAM целиком
(грабли дня 29). Через OpenAI-совместимый `/v1`, куда ходит opencode, параметр `num_ctx`
per-request **не передать**, поэтому контекст урезан **на уровне самой модели**: производные
модели созданы через `POST /api/create` с зашитыми `num_ctx` и параметрами сэмплинга.

Замеренный бюджет: реально доступно **~4 GiB VRAM** (не 6 — остальное держит десктоп).

| модель | всего | в VRAM | GPU/CPU |
|---|---|---|---|
| `qwen2.5-coder:7b-ctx16k` (Q3_K_M) | 4.60 GiB | 3.94 GiB | 86 / 14 |
| `qwen3:4b-ctx16k` (Q4_K_M) | 5.03 GiB | 3.88 GiB | 77 / 23 |

Стоимость KV-кэша считается по архитектуре и различается в разы:

- `qwen2.5-coder:7b` — 28 слоёв × 4 KV-головы → **56 KiB/токен** (16k ctx = 0.9 GiB)
- `qwen3:4b` — 36 слоёв × 8 KV-голов → **144 KiB/токен** (16k ctx = 2.25 GiB)

То есть 4B-модель платит за контекст в 2.5 раза дороже, чем 7B. Калькуляторы вроде canirun.ai
показывают только вес весов — на бюджете в 4 GiB это решающая разница.

### Находка 1: модель для кода ≠ модель для агента

`qwen2.5-coder:7b` (модель дней 26/29) **не исполняет протокол function-calling**: вместо
структурного вызова печатает его текстом в `content`.

```json
{"name": "grep", "arguments": {"pattern": "http.HandleFunc", "include": "*.go"}}
```

Проверено крест-накрест — причина в модели, не в обвязке:

| модель | путь | `tool_calls` |
|---|---|---|
| `qwen2.5-coder:7b` (база) | `/v1/chat/completions` | `null` |
| `qwen2.5-coder:7b-ctx16k` (производная) | `/v1/chat/completions` | `null` |
| `qwen2.5-coder:7b-ctx16k` | нативный `/api/chat` | `null` |
| `qwen3:4b` | нативный `/api/chat` | ✅ корректный вызов |

При этом шаблон `qwen2.5-coder` содержит `.Tools`/`.ToolCalls`, а ollama рапортует capability
`tools`. **Флаг отражает шаблон, а не фактическое поведение модели.** Агентный режим на этой
модели невозможен в принципе, поэтому рабочей моделью дня стала `qwen3:4b`.

### Находка 2: thinking у qwen3 отключается только правкой шаблона

Штатного выключателя у qwen3 в ollama нет — шаблон всегда открывает think-блок в префиксе
генерации. Обошли переопределением шаблона: `<think>\n\n</think>` предзакрыт, модель
`qwen3:4b-ctx16k-nothink`.

Эффект оказался косметическим: тегов `<think>` нет, но рассуждения переехали в `content`
(«Хорошо, мне нужно найти… Давай подумаю…»). Экономии токенов почти нет.

### Замер локальной модели (`qwen3:4b-ctx16k-nothink`, нативный API)

| | без правил | с правилами дня 36 |
|---|---|---|
| prompt | 188 токенов | **5341 токен** |
| prompt eval | — | 1011 tok/s |
| генерация | 2678 ток. @ **12.7 tok/s** | 843 ток. @ **5.8 tok/s** |
| итого | 231 с | 154 с |
| tool_call | ✅ | ✅ |

- **Правила дня 36 стоят ~5150 токенов** — треть 16k-контекста уходит только на них.
- **Скорость генерации падает вдвое при росте контекста** (12.7 → 5.8 tok/s): больший KV-кэш
  выдавливает слои на CPU. На этом железе контекст оплачивается не только памятью, но и скоростью.
- Правила при этом **работают**: с ними модель искала маршруты по `mux\.HandleFunc\(|mux\.Handle\(`,
  предварительно прочитав layout проекта из `CLAUDE.md`, — без правил шла наугад от `http.HandleFunc`.

## Задача A — генерация фичи (аналог дня 36)

Ветка `day39-a-feedback` от `mvp` (база `4ba5e8e`), дословный одношот-промпт дня 36
(`POST /api/v1/feedback`).

### Попытка 1 (протокол дня 36: один промпт, без уточнений) — провал

**22 мин 40 с, ноль изменённых файлов.** `git status` чист. Вместо реализации — пересказ задачи
в две строки:

> Add handler function to internal/api/api.go with validation and JSONL storage; write test in api_test.go

Причина видна в рассуждениях модели:

```text
But the maximum is 4 lines.
...
Given the strict line limit, the answer is:
Add handler function to internal/api/api.go with validation and JSONL storage; write test in api_test.go
That's 2 lines. It meets the requirements.
```

В системном промпте opencode действительно есть требование краткости — но с явной оговоркой:

> You MUST answer concisely with fewer than 4 lines of text **(not including tool use or code
> generation)**, unless user asks for detail.

Скобка выводит генерацию кода из-под лимита. **Модель эту оговорку не удержала** и применила
ограничение на объём текста к объёму работы: сочла, что уложиться в лимит важнее, чем выполнить
задачу, и отчиталась «That's 2 lines. It meets the requirements».

При этом план у неё был правильный — найти файлы хендлеров, добавить хендлер, валидацию, запись
в JSONL, написать тест, — и опирался на правила (`Server`-структура из `go-style`). Провал не в
понимании задачи, а в переходе от плана к действию.

### Попытка 2 (с явной директивой писать файлы) — код есть, но не собирается

В промпт добавлено: «ограничение на краткость ответа не распространяется на генерацию кода,
ты обязан реально создать файлы инструментами write/edit».

**38 мин 54 с.** Модель начала действовать, но первым же вызовом записала файл из **трёх байт**:

```text
← Write internal/api/feedback_handler.go
Wrote file successfully.
$ cat internal/api/feedback_handler.go

```

Буква указания исполнена (файл создан инструментом), суть — нет. Со второго вызова записала
настоящий код (1502 б) и добавила тест. Итог сборки:

```text
internal/api/feedback_handler.go:18:35: undefined: http    ← нет импорта "net/http", 6 мест
gofmt -l → оба файла не отформатированы
```

Дефекты против правил дня 36: теги через кавычки `"json:rating"` вместо бэктиков (формат тега
сломан, `recipe_id` не смапится), хелперы `decode`/`writeJSON`/`writeError` не использованы,
путь читается через `os.Getenv` мимо `config.Config`, godoc по-английски в русском проекте,
нет валидации длины комментария и UTC у метки времени, `Close()` не отложен, маршрут не
зарегистрирован.

**Дефект постановки (моя ошибка).** Промпт дня 36 взят дословно, но за прошедшие дни эндпоинт
`POST /api/v1/feedback` был вмержен в `mvp` (коммит `6397fde`) — то есть задача просила
реализовать то, что уже есть. Сборка падала в том числе на
`method Server.handleFeedback already declared`. Показательно, что модель читала кодовую базу,
но существующую реализацию не заметила и написала конфликтующий дубль.

Урок для методики: **промпт из прошлого задания нельзя переиспользовать вслепую — целевая фича
могла уехать в основную ветку.** Поэтому прогон повторён на чистой базе.

### Попытка 3 (чистая база, протокол дня 36) — провал

Ветка `day39-a-feedback-v2` от **`70722dd`** — это ровно тот коммит правил v2, от которого
гналась облачная `gen2` дня 36. База в базу, промпт дословный, без добавок.

**~43 минуты (прерван), ноль изменений в репозитории.** Единственный вызов записи ушёл по
**выдуманному пути вне репозитория**:

```text
← Write /home/user/project/internal/api/handlers/feedback.go
Wrote file successfully.
```

Рабочий каталог — `/home/development/personal/fridge-chef`, и он был в контексте вместе
с `CLAUDE.md`. Модель подставила generic-путь «/home/user/project», а opencode с `--auto`
создал всё дерево каталогов и записал туда без возражений.

Код в этом файле был **лучше** предыдущей попытки — бэктики с `omitempty`, хелпер `writeError`,
сообщения об ошибках по-русски (правила дня 36 работают), — но импорта `"net/http"` снова нет.

Дальше модель **потеряла задачу**. Финальные рассуждения:

> Wait, the instructions say not to guess URLs, but the user didn't provide a URL yet.
> They just asked about opencode. […] I'll call webfetch with url: "https://opencode.ai".

Про opencode никто не спрашивал. Это исчерпание контекста: 16k заполнились (5.1k правил +
системный промпт opencode + накопленные раунды), исходная задача вытеснилась из окна, и модель
начала отвечать на его обрывки. Прогон остановлен вручную.

**Побочный вывод про безопасность:** `--auto` в связке с моделью, выдумывающей абсолютные пути,
означает запись в произвольное место файловой системы. Никакого ограничения по путям opencode
не применил. Для автономных прогонов на слабой модели нужна изоляция (контейнер/worktree),
а не доверие к тому, что агент останется в рабочем каталоге.

## Задача B — агентный bug-fix (аналог дня 37)

Ветка `day39-b-bugfix` от `mvp` (`4ba5e8e`). Баг настоящий и на момент дня 39 не закрыт:
валидации продуктов в `mvp` нет (`validateProducts`/`validProduct` отсутствуют, `normalize`
только канонизирует имена), поэтому не-кулинарный ввод доезжает до LLM. Промпт — симптом
без диагноза, дословно из дня 37.

**Результат: провал за 14 мин 46 с. Ноль вызовов инструментов, ноль изменений.**

Модель **ни разу не открыла код**. Вместо расследования выдала прозой правдоподобное описание фикса:

```text
The fix needed is to add validation logic similar to the `handleSuggest` function
(which checks for products) to the `handleRecipe` function.
```

Формально направление верное — но получено не из кода, а из правил в системном промпте:
имена `handleRecipe`, `handleSuggest`, `req.Products` есть в `CLAUDE.md` и примерах `go-style`.
То есть модель пересказала контекст, который ей дали, и выдала это за диагноз.

Ни одного пункта протокола дня 37 не выполнено: симптом не воспроизведён, причина не подтверждена
ссылкой `файл:строка`, фикса нет, регрессионного теста нет, `go test`/`vet`/`gofmt` не запускались.

Показательно сравнение с днём 37: там облачный профиль `bug-fix` **тоже** ошибался — но ошибался
содержательно, проверяя фикс не по тому пути (API вместо UI), и это лечилось доработкой профиля.
Здесь дорабатывать нечего: агент не дошёл до стадии, на которой профиль вообще начинает работать.

**Самое неприятное для облака в этой таблице** — две строки про дефекты. Оба места, где
`MiniMax-M2.5` промахнулся (руны против байтов и `.gitignore`), Claude Code на **идентичной
задаче с идентичными правилами** отработал верно. Причём гигиена рантайм-данных была прямым
целевым рычагом правил v2 дня 36 — то есть правило было написано специально под этот случай
и всё равно сработало только на более сильной модели.

Это ровно продолжение вывода дня 36 («правила — страховой полис, а не рычаг») и дня 37
(«текстовое требование исполняется ненадёжно, структурное — всегда»): **чем слабее модель,
тем меньше правил она способна конвертировать в код**, и деградация идёт не плавно, а обвалом —
от «выполняет всё» через «выполняет основное, теряет детали» до «пересказывает правила
вместо работы».

## Для чего локальной модели хватает

**Хватает:**

- **Read-only вопросы по кодовой базе** — единственный класс, где локалка отработала верно
  (пре-флайт: 5 эндпоинтов с файлами и строками, совпало с эталоном дня 37). Цена — 16 минут
  на вопрос, но ответ правильный, и данные не покидают машину.
- **Приватный контур как жёсткое требование.** Если код нельзя отдавать наружу, локальная
  модель — не выбор между быстрым и медленным, а выбор между медленным и никаким.
- Разовые изолированные вопросы к модели без агентного цикла (объясни код, набросай функцию) —
  то, что уже делалось в днях 26–30.

**Не хватает:**

- **Любая работа с записью в репозиторий.** Три прогона задачи A не дали ни одного собирающегося
  файла. Модель либо описывает работу вместо выполнения, либо пишет заглушку из трёх байт,
  либо промахивается мимо рабочего каталога.
- **Агентный цикл длиннее 2–3 раундов.** При 16k контекста и 5.1k, съеденных правилами, задача
  вытесняется из окна — в задаче A модель к концу отвечала на обрывки системного промпта.
- **Автономная работа без человека** — цель всего advanced-блока. Здесь она недостижима:
  за 2 часа суммарных прогонов полезного результата ноль.

**Рекомендация:** на этом железе локальная модель — инструмент **чтения**, а не **записи**.
Разумная связка: локалка отвечает на вопросы по коду и работает в приватном контуре,
запись в репозиторий и агентные циклы остаются за облаком.

## Выводы

Задание требовало настроить локальную модель как код-ассистент и честно сравнить с облаком.
Настроить — получилось. Сравнение вышло не «локалка медленнее», а «локалка не работает как агент».

### Что работает

- **Харнес собран и правила доехали.** opencode + ollama, правила дня 36 через `instructions`
  без заведения `AGENTS.md`. Влияние правил доказано наблюдением, а не декларацией: с ними модель
  искала маршруты по `mux\.HandleFunc\(`, прочитав layout из `CLAUDE.md`, без них — наугад от
  `http.HandleFunc`. Дальше она воспроизводила из правил и `Server`-структуру, и хелпер `writeError`,
  и русские сообщения об ошибках.
- **Обход ограничения `num_ctx`.** Через OpenAI-совместимый `/v1` контекст per-request не
  передаётся (грабли дня 29), поэтому производные модели с зашитым `num_ctx` создавались через
  `POST /api/create` прямо по туннелю — без доступа к ФС удалённой машины.
- **Read-only работа локально возможна.** Единственный успех: вопрос про эндпоинты — ответ верный,
  совпал с эталоном дня 37. Цена — 15 мин 53 с, из них ~14 минут рассуждений перед одним `grep`.

### Что не работает

- **Запись в репозиторий — ноль из трёх.** Задача A провалена трижды подряд, каждый раз по новой
  причине: описание вместо работы (22 мин) → файл-заглушка `...` из трёх байт и несобирающийся
  код (39 мин) → запись мимо репозитория в `/home/user/project` и потеря задачи (43 мин).
- **Агентный bug-fix — ноль вызовов инструментов за 15 минут.** Модель не открыла код вообще,
  а пересказала правила из системного промпта и выдала это за диагноз.
- **Контекст 16k не вмещает работу.** Правила стоят 5341 токен — треть окна. Плюс системный промпт
  opencode с tool-схемами. К третьему-четвёртому раунду исходная задача вытесняется, и модель
  начинает отвечать на обрывки промпта (в задаче A — предлагала скачать документацию opencode).
- **Контекст оплачивается дважды.** Не только памятью, но и скоростью: 12.7 → 5.8 tok/s при росте
  промпта, потому что KV-кэш выдавливает слои на CPU (GPU 77% вместо 100%).

### Главное

**Барьер оказался не в железе, а в способности модели исполнять протокол инструментов.**
Из семи моделей на машине агентный цикл тянет ровно одна — `qwen3:4b`. И три разных режима отказа
на одном и том же харнесе:

| модель | режим отказа |
|---|---|
| `qwen2.5-coder:7b` (локально) | вызовов не делает — печатает JSON в текст |
| `GigaChat3-10B-A1.8B` (облако) | вызовы битые — падает схема аргументов, opencode крашится |
| `Qwen3-Coder-Next` (облако) | задаёт уточняющие вопросы вместо работы; с запретом на вопросы — зависает |

Отсюда три вещи, которые я бы записал как переносимые:

1. **Модель для кода ≠ модель для агента.** `qwen2.5-coder:7b` — та самая, что отлично отвечала
   в днях 26–30, — для агентного харнеса непригодна в принципе. Заявленная capability `tools`
   в ollama отражает **шаблон**, а не поведение модели: проверять надо прогоном, не флагом.
2. **Слабая модель ломается на оговорках.** Системный промпт opencode прямо исключает генерацию
   кода из лимита краткости — «fewer than 4 lines *(not including tool use or code generation)*».
   4B-модель оговорку не удержала и сочла, что уложиться в лимит важнее, чем выполнить задачу.
   Это прямое продолжение дня 37: невыполнение должно быть **наблюдаемо**, иначе инструкция
   исполняется формально. Здесь она исполнилась формально дважды — сначала отчётом вместо работы,
   потом файлом из трёх байт.
3. **`--auto` без изоляции опасен.** Модель выдумала абсолютный путь, и opencode создал дерево
   каталогов вне репозитория и записал туда. Для автономных прогонов на слабой модели нужен
   контейнер или worktree, а не надежда, что агент останется в рабочем каталоге.

### Замечания

- **Своя ошибка в методике:** промпт дня 36 взят дословно, а эндпоинт `feedback` за прошедшие дни
  уехал в `mvp` — первый прогон задачи A оказался поставлен на уже реализованную фичу. Урок:
  промпт из прошлого задания нельзя переиспользовать вслепую, база должна сверяться. Перегнал
  от `70722dd`. Показательно, что модель существующую реализацию не заметила и написала дубль.
- **Отключение thinking у qwen3 — только правкой шаблона** (предзакрытый `<think></think>`),
  штатного выключателя в ollama нет. Эффект косметический: теги пропали, рассуждения переехали
  в `content`, экономии токенов почти нет.
- **Правила деградируют не плавно.** На том же промпте с теми же правилами: Claude Code закрыл
  и лимит в рунах, и `.gitignore`; `MiniMax-M2.5` — ни того, ни другого, хотя `.gitignore` был
  прямым целевым рычагом правил v2 дня 36; локальная 4B правила пересказала, но в код не перенесла.
- **Автокомплит не делался** — opencode агентный инструмент, а не autocomplete-плагин. Модель
  для FIM (`fridge-fim:1.5b-ctx2k`) на машине есть, но связка под неё — отдельная задача.
- **Усиление (перебор 2–3 моделей ради оптимальной связки) пропущено** по договорённости. Де-факто
  перебор всё равно случился — вынужденный, из-за отказов: три локальные и три облачные модели.
