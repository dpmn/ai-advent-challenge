### Отправная точка

Тесты в fridge-chef уже были — по одному `*_test.go` на каждый пакет, покрытие 80–96%

покрывать, и сам доказывает результат.

### Уровень 1 — профиль `test-writer` (`.claude/agents/test-writer.md`)

Инструменты: `Read, Glob, Grep, Bash, Edit, Write`.

- Сам замеряет базу (`go test -coverprofile` + `go tool cover -func`), сам отбирает дыры.
  Приоритет задан **критериями важности** (инварианты проекта → ветки ошибок и границы →
  функции с нулевым покрытием), а не списком файлов: что именно покрывать, ему не говорят.
- Правит **только `*_test.go`**. Нашёл настоящий баг — не чинит, а описывает в разделе
  «Найден баг» (файл:строка, ожидание, факт, команда воспроизведения); починка — работа `bug-fix`.
- Запрет ослаблять и удалять чужие тесты, добавлять зависимости, ходить в сеть из тестов.
- Требование проверять тест на «падает ли, если сломать проверяемое место» — с записью в отчёт.

### Уровень 2 — профиль `smoke-runner` (`.claude/agents/smoke-runner.md`)

Инструменты: `Read, Glob, Grep, Write` + инструменты Playwright MCP.

Три структурных запрета вместо текстовых обещаний (прямое применение вывода дня 37 — отсутствие
инструмента работает безотказно, текстовое требование ненадёжно):

- **нет `Edit`** — не может чинить код по ходу прогона;
- **нет `Bash`** — не поднимает и не гасит сервис, не лезет в систему;
- **не выдан `browser_evaluate`/`browser_run_code_unsafe`** — не может выдернуть результат скриптом
  и объявить шаг пройденным; вывод делается только из снапшота страницы, как у пользователя.

При падении локализует место по коду (у него есть чтение) и отдаёт гипотезу `файл:строка`,
явно помеченную как гипотеза.

### Сценарии — `docs/testing/smoke-scenarios.md`

Логина и CRUD в продукте нет, поэтому шаблон из задания переведён на язык визарда. Пять сценариев:

| # | сценарий | LLM |
|---|---|---|
| S1 | продукты → кандидаты → «Готовим! 🍳» → текст рецепта | да |
| S2 | «Состав» (`mode=strict`) — рецепт из корпуса, быстрее 15 с | нет |
| S3 | возвраты назад: список кандидатов и поле продуктов сохранены | нет |
| S4 | пустой ввод и строка из одних запятых → ошибка, запрос не уходит | нет |
| S5 | мусорный ввод → кандидатов нет → «✨ Придумай блюдо» | да |

Селекторы точные и стабильные (`#products`, `#btn-suggest`, `button[data-mode][data-id]`,
`#recipe-text`, `#btn-creative`). Тексты рецептов от живой модели каждый раз разные — проверяется
непустота и отсутствие ошибки, а не конкретные слова.

### Связка в один цикл — команда `/qa` (`.claude/commands/qa.md`)

Два профиля запускаются **не руками по очереди**: человек вызывает `/qa` один раз, дальше без него.
Оркестрация именно на команде главного агента, потому что субагент не может вызвать субагента.

```
подготовка (каталог прогона, chmod на папку скриншотов, проверка наличия MCP)
   ↓
L1: Agent → test-writer   (без подсказок, что покрывать)
   ↓
ворота: go test ./... && go vet ./... && gofmt -l .   ← красное = smoke НЕ запускается
   ↓
go build → запуск бинарника в фоне → ждать 200 на /healthz (до 60 с)
   ↓
L2: Agent → smoke-runner  (файл сценариев + BASE_URL + каталог отчёта)
   ↓
kill сервиса, перенос скриншотов, единый отчёт docs/testing/runs/<дата>/report.md
```

Ворота между уровнями осмысленны: тыкать UI на красной сборке бессмысленно. Оркестратор проверяет
их **сам**, не доверяя формулировкам профиля. Зелёный вердикт при недостающих артефактах
(нет скриншотов, нет профилей покрытия) запрещён явно.

### Инфраструктура Playwright MCP (`.mcp.json`)

На машине не было ни `node`, ни `npx`, ни браузеров, `DISPLAY` пуст. Поэтому — официальный
docker-образ, хост чистый:

```json
"playwright": {
  "command": "docker",
  "args": ["run","-i","--rm","--init","--network","host",
           "-v","${CLAUDE_PROJECT_DIR:-...}/.claude/runs/smoke:/output",
           "-w","/output","mcr.microsoft.com/playwright/mcp","--headless","--output-dir","/output"]
}
```

Проверено вживую до написания профилей (JSON-RPC-проба в контейнер): сервер отдаёт 24 инструмента,
`--network host` даёт контейнеру доступ к локальному `:8080`, страница fridge-chef рендерится,
скриншот сохраняется на хост. Три грабли, которые проба и вскрыла:

1. stdin нельзя закрывать сразу — сервер гасится раньше, чем отработает браузер;
2. каталог под `/output` должен быть доступен на запись непривилегированному пользователю
   контейнера (иначе `EACCES`), поэтому в `/qa` есть `chmod 777`;
3. без `-w /output` скриншоты уходят в рабочий каталог контейнера и умирают вместе с ним.

### Усиление

Не делали — по договорённости nice to have. `/qa` при этом и есть кирпич, который вешается
на пост-PR хук, когда до него дойдут руки.

## Сценарий проверки

Проверяется **автономность цикла**: одна команда — и до отчёта человек не вмешивается.

### Подготовка

```bash
# образ Playwright MCP (~2 ГБ, тянется один раз)
docker pull mcr.microsoft.com/playwright/mcp

cd /home/development/personal/fridge-chef
git checkout testing
# .env с LLM_BASE_URL / LLM_API_KEY / LLM_MODEL и корпус ./corpus/v001 должны быть на месте:
go run ./cmd/fridge-chef   # → «корпус v001: 5000 рецептов», Ctrl+C
```

Порт `8080` должен быть свободен — `/qa` поднимает сервис сам и откажется работать по чужому
процессу.

### Прогон

**Свежая сессия** Claude Code в `/home/development/personal/fridge-chef` — иначе MCP-сервер
из `.mcp.json` не подхватится. На старте сессии подтвердить сервер `playwright`.

```
/qa
```

Дальше не вмешиваться. Ожидаемый ход (10–20 минут, из них живые вызовы LLM — до минуты каждый):

1. агент вызывает `test-writer`; тот меряет покрытие, выбирает дыры **сам**, пишет тесты,
   гоняет `go test`;
2. агент сам прогоняет ворота `go test ./... && go vet ./... && gofmt -l .`;
3. собирает бинарник, поднимает в фоне, ждёт `200` на `/healthz`;
4. вызывает `smoke-runner`; тот проходит S1–S5 в headless-браузере, снимая скриншот на каждом
   помеченном шаге;
5. гасит сервис, переносит скриншоты, пишет единый отчёт.

### Что считаем успехом

```bash
cd /home/development/personal/fridge-chef

go test ./... -cover     # зелёно; покрытие выше базы:
                         # api 87.3 / corpus 86.0 / feedback 86.7 / llm 80.0 /
                         # match 94.4 / generate 95.2 / config 96.3
go vet ./... && gofmt -l .   # чисто, вывод gofmt пуст

git status --short           # ≥3 изменённых/новых *_test.go, продуктовый код НЕ тронут
ls docs/testing/runs/*/screenshots/   # скриншоты по шагам сценариев
cat docs/testing/runs/*/report.md     # вердикт, L1 (покрытие было→стало), L2 (таблица сценариев)
```

Критерии:

- **L1**: затронуто ≥ 3 файлов тестов, финальный прогон зелёный, диффа в непроверочном коде нет.
- **L2**: 5 сценариев прогнаны, у каждого явный результат и скриншоты; S5 допускает `skipped`,
  если на мусорный ввод внезапно нашлись кандидаты — это честная фиксация, а не провал.
- **Цикл**: между `/qa` и итоговым отчётом человек не сделал ни одного действия.

### Что получилось

**Цикл действительно автономен.** 20 минут 17 секунд, одна команда, ноль вмешательств человека
между запуском и вердиктом. Внутри: `test-writer` — 41 вызов инструментов, 8 мин 32 с;
`smoke-runner` — 69 вызовов, 8 мин 46 с; между ними оркестратор сам прогнал ворота, собрал
бинарник, поднял сервис, дождался `/healthz`, погасил и склеил отчёт. Это и был критерий дня.

**Уровень 1: 83.7% → 92.5%.** Семь новых файлов тестов (~49 тестов), продуктовый код не тронут.
По пакетам: `config`, `corpus`, `generate`, `match`, `web` — 100%, `api` 87.3 → 96.1, `llm` 80.0 → 95.0.

**Мутационная проверка — сильнейший ход прогона, и он не был приказан.** В профиле стояло мягкое
«сомневаешься — временно сломай проверяемое место и убедись, что тест покраснел». Профиль сделал
это систематически: **7 мутаций продуктового кода, каждая откачена `git checkout --`, все семь дали
красный тест**. Расширил кламп лимита, отключил проверку дубликата id, снял тай-брейк по `Matched`,
пометил битый JSON как retriable, проигнорировал ошибку `feedback.Append`, сменил дефолтный режим,
отключил поиск в `canon`. Это ровно та разница между «покрытие выросло» и «тесты ловят регрессии»,
доказанная фактом, а не заявленная.

**«Сам выбирает» отработало и в сторону отказа.** Профиль не стал гнать покрытие ради процента:
`cmd/fridge-chef` (0%) оставил как склейку без логики, в `feedback` показал, что остались
недостижимые ветки (`json.Marshal` структуры без нетипизируемых полей). Честное «покрывать нечего»
он предпочёл накрутке — то есть критерии важности в промпте сработали лучше, чем список файлов.

**Уровень 2: 5 из 5 на живой модели.** S1 — генерация ~40 с, S5 (creative) ~90 с при лимите 120 с;
strict отвечает ≈1 с, то есть в LLM действительно не ходит — это подтвердилось наблюдением, а не
допущением. 13 скриншотов, консоль чистая кроме известного `404 /favicon.ico`. Профиль сверх
сценария сделал контрольный замер скорости strict и честно пометил его как «сверх шагов сценария».

**Структурные запреты снова отработали безотказно.** У `smoke-runner` не было ни `Bash`, ни `Edit`,
ни `browser_evaluate` — он физически не мог ни починить упавшее, ни выдернуть результат скриптом
в обход снапшота. Ни одной попытки обойти это в логе нет.

**Ворота сработали как ворота.** Оркестратор прогнал `go test/vet/gofmt` сам, не поверив
формулировкам профиля. В этом прогоне всё было зелёное, поэтому проверка ворот на красной сборке
осталась непройденной — это дыра в доказательстве, а не подтверждённое поведение.

### Что вскрылось

1. **Профилю не хватило прав записать свой же отчёт.** `smoke-runner` не смог создать
   `report-smoke.md` в каталоге прогона — файл положил оркестратор с его слов. Обидная деталь:
   контракт «профиль пишет отчёт сам» на деле не выполнился, а вердикт всё равно вышел зелёным.
   Цена структурного подхода: срезав инструменты, надо явно оплатить то, что профилю всё-таки нужно.
2. **Относительные имена скриншотов в Playwright MCP резолвятся в корень репозитория**, а не в
   `--output-dir`: `ENOENT .../fridge-chef/s1-01-start.png`. Профиль обошёл сам, передав полный путь
   `/output/<имя>.png`, и записал это в замечания. В моей пробе перед реализацией этого не всплыло —
   проба ставила `-w /output` и относительное имя срабатывало; в реальной сессии поведение другое.
   Вывод на будущее: проба доказывает, что канал работает, но не воспроизводит контекст клиента.
3. **Внутренний таймаут MCP-обёртки 5000 мс** уронил первое ожидание спиннера в S5; повтор прошёл
   штатно. Ожидание дольше пяти секунд надо строить циклом, а не одним `browser_wait_for`.
4. **Сервис не умер с первой попытки** — оркестратор заметил, что `/healthz` ещё отвечает, и
   разобрался со второго захода. Хорошо, что заметил (проверка «процесс действительно умер» была
   в инструкции), плохо, что убийство по PID оказалось ненадёжным.

Плюс две находки по продукту, не блокирующие: `Candidate.Recipe.Ingredients` разделяет массив с
активным корпусом (`internal/match/match.go:83`) — инвариант «активная версия иммутабельна» держится
на дисциплине вызывающих; GET на POST-эндпоинты отдаёт 404 вместо 405, потому что маршрут статики
перехватывает раньше.

### Главный вывод дня

Ценность оказалась не в тестах, а в **воротах и в доказательствах**. Тесты агент пишет и сам;
разница между «отчитался» и «проверено» создаётся двумя вещами: оркестратор перепроверяет ворота
своими руками, а профиль доказывает тесты мутацией. Всё остальное — оформление.

И обратная сторона: дыра в доказательстве нашлась ровно там, где всё прошло гладко. Красную сборку
цикл в этом прогоне не видел, значит поведение ворот на отказе — пока обещание, а не факт.
